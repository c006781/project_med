# Старый слой — сведения перед заменой

Для разработчиков. Что делал заменяемый код, почему так устроен, где ошибки и подводные
камни — чтобы новый слой не повторил старых ошибок и ничего нужного не потерял.

Режим «Старый слой» (`_dev/ДОГОВОРЁННОСТИ.md`, 25.10.2026): при замене сведения — сюда, код
**остаётся**; удалить ненужное — в конце переработки (`_dev/ПЛАН.md` Ф4.8). Разделы — по
заменяемым модулям; дата — когда сведения собраны. Полное описание дальше — Ф2.5.1 (М22).

---

## 1. Черновики старых экранов: `app/draft/draft_registry.py`, `editable_component.py`, `ihierarchical_editable.py`

Собрано 2026-10-31 (М16). Подробный разбор ошибок — `app/draft/IMPLEMENTATION.md` §1, §3;
характеризующие тесты — `tests/test_drafts/test_legacy_behavior.py`.

**Чем заменено:** переносимый пакет `app/utils/drafts` (`DraftStore`, план сохранения,
исполнение одной транзакцией) и `app/utils/drafts_qt`; связка с приложением —
`app/draft/integration.py` (`create_app_drafts`, одно хранилище на главное окно).

**Кто ещё пользуется старым** (на 2026-10-31): `interfaces/gui/gui_window/pages/paginated_list_page.py`,
`mixins/draft_tree_mixin.py`, `frames/appointment_photo_frame.py`,
`widgets/delegate/image_delegate.py`, запасные старые страницы в `main_window.py` (если новое
хранилище не создалось). Новые экраны (`draft_pages.py`, М21) старое не используют.

### 1.1 `DraftRegistry` — что делал

* Плоское хранилище `ключ → словарь` (QObject, сигнал `draft_changed(key, has_draft)`) плюс
  подписки на точный ключ и на префикс (обратные вызовы).
* Смысл — в формате ключей: `{тип}:{id}:draft` (изменённая строка, `{"dto": model_dump}`),
  `{тип}:{id}:{подсистема}` (черновик компонента, `appointment:123:photos`),
  `__new__:{тип}:{temp_id}` (новая строка, `temp_id < 0`), `__deleted__:{тип}:{id}`,
  `__status__:{тип}:{id}` (`own` / `child` / `both`), `__counter__:{тип}:{parent_id}`
  (потомки с изменениями), `__parent_counter_inc__:{тип}:{temp_id}` (балансировка счётчика).
* Поддеревья — по префиксу ключа (`discard_subtree_by_prefix`, `apply_by_prefix`).
* Применение: `apply_and_clear(key, applier)` — вызвать сохранение, при успехе удалить
  черновик; при исключении черновик остаётся (повторная попытка возможна).
* DTO-помощники: `save_draft_dto` / `load_draft_dto`, `get_new_dtos` (новые строки типа),
  `merge_new_dtos` (новые строки к странице из БД, без дублей по id, сортировка — новые
  с отрицательными id первыми), `update_foreign_key_in_new_dtos` (замена временного id
  родителя на настоящий после сохранения).

### 1.2 `IEditableComponent`, `EditableComponentMixin`, `IHierarchicalEditableComponent`

* Интерфейс виджета, хранящего свой черновик в реестре (фото-загрузчик и т. п.): ключ
  `{тип}:{parent_id}:{подсистема}`, `save_to_registry` / `load_from_registry`,
  `has_changes`, `apply` (сохранить в БД и удалить черновик), `discard`.
* Уведомление родителя о числе черновиков — обратный вызов `set_draft_change_notifier`,
  `(parent_id, ±1)` при каждом создании / удалении; без него счётчики страницы врут.
* Подписка на свой ключ: изменился черновик — компонент сам перечитывает его; при смене
  строки родителя — `update_parent_id` с переподпиской на новый ключ.
* Дерево компонентов (`add_child` / `remove_child`, `has_descendant_changes`).

### 1.3 Решения и почему

* **Ленивые свойства вместо атрибутов в `__init__`** (`EditableComponentMixin`): миксин
  стоит в множественном наследовании с виджетами Qt; не каждый наследник вызывает
  `super().__init__` по всей цепочке, — атрибуты создаются при первом обращении
  (`AttributeError` → значение по умолчанию). Новый слой держит состояние вне виджетов
  (хранилище), так что приёма не требует.
* **`QABCMeta`** — метакласс, совмещающий `QObject` и `ABC` (иначе конфликт метаклассов);
  с 2026-10-16 — общий объект `app/utils/qt_meta.py` (был импорт из слоя интерфейса).
  Проверку абстрактности он не делает (QM1, решение владельца В-5: пометка до М21, в
  новых экранах — проверка).
* **Ошибки обратных вызовов** подписчиков ловятся и пишутся в журнал — один сломанный
  подписчик не рвёт уведомление остальных.

### 1.4 Ошибки и подводные камни (не переносить)

* D1 — у каждого фрейма свой реестр: изменения разных экранов разом не сохранить.
* D2 — «Приёмы и фото» сохраняются двумя транзакциями (не атомарно).
* D3 — родитель ищется по строке, загруженной сейчас: после перехода на другую строку /
  фрейм статусы и счётчики сбиваются.
* D4 — подъём статуса вызывается без типа (`__status__:None:…`) — `xfail`.
* D5 — кеш статусов по id без типа: приём №5 и фото №5 смешиваются — `xfail`.
* D6 — счётчики на парных `+1 / −1` из многих мест; в `inc_child_counter` счётчик
  обрезается снизу нулём (`max(0, …)`) — признак расхождения, а не исправление.
* D7 — связи родитель / потомок — в переопределениях каждой страницы, тип родителя —
  подменой `self._entity_type` на время вызова.
* D8 — нет атомарного «сохранить ветку» с новыми родителями и подтверждения удаления.
* D10 — `update_foreign_key_in_new_dtos` и `get_new_dtos` ищут атрибут у `data['dto']`, а
  там словарь: временный id родителя у новых детей не заменяется — `xfail`.
* D11 — после отмены изменения ребёнка статус `child` у родителя не снимается — `xfail`.
* `editable_component.py`: 6 замечаний pyflakes (`except … as e` без `e` в ленивых
  свойствах), 19 функций без докстринга — не исправлялось (код уходит в Ф4.8; докстринги —
  Ф4.2а, если код останется).

### 1.5 Что из требований владельца закрывает новый слой

Требования 2026-10-15 (`app/draft/IMPLEMENTATION.md` §2): одно хранилище на всё
приложение (D1), сохранение одной транзакцией (D2), объём сохранения «цель × направления»,
новые родители — предупреждение и цепочка, удаление ветки — подтверждение со списком,
черновики только в памяти и вопрос при закрытии — всё в `app/utils/drafts` и
`app/draft/integration.py`; тесты — `tests/test_drafts/test_core*.py`,
`test_integration_services.py`. Черновики данные БД сами не удаляют (В-18, В-19).
