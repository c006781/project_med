## 1. Зачем миграции

До 2026-10-16 база создавалась `Base.metadata.create_all`. Он только СОЗДАЁТ недостающие
таблицы: новый столбец, индекс или изменение типа в существующей базе не применяется. Базы,
созданные в разное время, расходились со схемой — у настоящей базы проекта не было индекса
`ix_appointment_note_text`, который есть в модели.

## 2. Как работает (`upgrade_database`, вызывается из `Database.__init__`)

| База | Что происходит |
|---|---|
| новая (пустая) | все миграции с первой |
| с отметкой версии (`alembic_version`) | недостающие миграции; перед ними — резервная копия файла |
| старая без отметки (create_all) | приведение к исходной схеме `0001_baseline` (см. §3) → отметка → дальнейшие миграции |
| последняя версия | ничего (файл не трогается) |

* **Резервная копия** перед любым изменением существующей базы-файла:
  `<файл>.bak-<ГГГГММДД_ЧЧММСС>-<версия>` (для старой базы — `-legacy`).
* **Транзакции (M1).** Драйвер SQLite (pysqlite) фиксирует CREATE/ALTER/DROP сам, мимо
  транзакции — сбой посреди миграции оставил бы базу полуобновлённой. Миграции идут через
  отдельный движок с настоящими транзакциями (рецепт SQLAlchemy: драйвер не управляет
  транзакциями, `BEGIN` — явно): сбой — откат ВСЕГО, включая DDL. Основной движок
  приложения не меняется.
* `render_as_batch=True` — SQLite почти не умеет ALTER TABLE, Alembic пересобирает таблицу.
* `create_tables(recreate=True)` удаляет и `alembic_version` — иначе пустая база считалась бы
  свежей.

## 3. Старые базы без отметки версии

Сравнение — со схемой, которую строит САМА исходная миграция (во временной базе в памяти),
а не с текущими моделями (они меняются).

| Отличие | Что делаем |
|---|---|
| нет таблицы / индекса / необязательного столбца | **дописываем** (create_all этого не делал — базы разных лет отличаются) |
| лишнее: старые столбцы (`email`), посторонние таблицы, другие индексы, иные типы | **не трогаем** — данные не теряются; предупреждение в журнал |
| нет обязательного столбца без значения по умолчанию | **отказ** (`MigrationError`), база не меняется |

Ограничение: дописанный недостающий столбец — без внешнего ключа (SQLite не умеет
добавить связь к существующей таблице без пересборки; Alembic упал бы). Данные это не
затрагивает; связь появится, если позже миграция пересоберёт таблицу.

## 4. Как добавить изменение схемы

1. Изменить модель в `database_shema/clinic.py`.
2. Создать миграцию (из корня проекта; консоль работает с ОТДЕЛЬНОЙ базой разработчика
   `migrations_dev.db`, не с настоящей — M11):
   `alembic -c app/database/migrations/alembic.ini upgrade head` — довести её до текущей версии;
   `alembic -c app/database/migrations/alembic.ini revision --autogenerate -m "что меняем"`.
3. Вычитать файл в `migrations/versions/`, дописать «что меняет и почему».
4. Тест `test_models_match_migrations` упадёт, если модель изменили, а миграцию нет.
5. Настоящая база обновится сама при запуске программы (копия, блокировка, проверки).

**Правила для миграций** (они же — в шаблоне `script.py.mako`):

* Модели приложения в миграциях НЕ импортировать: модели меняются, миграция — нет. Для
  данных — `op.execute(...)` или `sa.table('patients', sa.column('phone'))`.
* Применённую (выпущенную) миграцию не менять и не удалять — только новая поверх.
* `downgrade` — обратное действие; если обратного нет (удалённые данные) — явный
  `raise` с объяснением, а не тихая заглушка.
* Изменение столбца/ограничения в SQLite — через `op.batch_alter_table` (autogenerate
  делает так сам: `render_as_batch`). Таблица пересобирается; внешние ключи на это время
  выключены (M10), после миграции проверяется, что новых «висячих» ссылок нет.
* Данные + схема — в одной миграции можно: всё в одной транзакции, сбой — откат всего.
* **Имена связей.** У моделей — правило именования `NAMING_CONVENTION` (`clinic.py`, A2):
  новые внешние ключи получают имя `fk_<таблица>_<столбец>_<куда>`. У ключей в базах,
  созданных до 2026-10-18, имён нет. Удалить/изменить такую связь —
  `op.batch_alter_table('photos', naming_convention=NAMING_CONVENTION)` и дальше по имени
  из правила (проверено тестом на старой базе). Из приложения в миграции можно брать
  только `NAMING_CONVENTION` (постоянна; правило «модели не импортировать» — про классы).
* Две ветки разработки добавили миграции от одной версии — две «головы»: программа
  откажется запускаться, нужна миграция-слияние (`alembic merge heads`).

Имена файлов миграций — латиницей (`0001_baseline.py` …).

**Запуск разных версий программы на одной базе.** Новая база + старая программа
(версия базы ей неизвестна) — отказ с понятным сообщением, база не трогается (M9).

* Таблица `test_prescriptions` в настоящей базе проекта (пустая, создана моим тестом до T2) —
  удалена 2026-10-18 по решению владельца: перед этим копия
  `clinic.db.bak-20261018_173228-before-drop-test_prescriptions`, проверено — таблица пуста,
  остальные данные совпадают (20 пациентов, 47 приёмов, 495 заметок, 21 фото), integrity ok.
* Сборка exe: миграции — внутри пакета `app` (PyInstaller `--add-data app`), `alembic.ini` в
  работе не нужен. Проверено сборкой PyInstaller (папкой и одним файлом) — проход 6.
  Миграция, импортирующая модуль, которого нет в остальной программе, в exe упадёт —
  такой модуль добавить в скрытые импорты `scripts/build_win.py`.
* Поиск ссылок на заметки (`NoteService._note_references`) учитывает только таблицы,
  существующие в базе: модель могли добавить, а миграцию ещё не применить.
* **Отложенные удаления и действия сессии** (`session._deletions`, `session._actions`;
  2026-10-30, ТД-9). `Database.Session` — `scoped_session`: одна сессия на поток, `close()`
  её не заменяет, списки живут дольше транзакции. Поэтому обработчик `after_commit`
  выполняет «после коммита» и **отбрасывает** «при откате», `after_rollback` — наоборот;
  иначе чужую запись выполнила бы следующая транзакция потока (удалялся сохранённый файл
  фото). Неудавшееся удаление (файл занят) помечается `retry` и не отбрасывается — его
  повторит следующее событие того же вида. `rollback()` без начатой транзакции (в блоке не
  было запросов) SQLAlchemy событий не шлёт — `session_scope` перед откатом начинает пустую
  транзакцию (соединение не открывается). Сессия, полученная `get_session()` и откаченная
  без транзакции вручную, этой защиты не получает. FD10 (2026-10-31): удаление «после
  коммита», запланированное при неактивной сессии (flush упал, коммита не будет), файл не
  трогает — предупреждение в журнал (`app/utils/IMPLEMENTATION.md`, FD10); раньше
  `schedule_deletion` удалял сразу.

## 9. Исключения базы и значения запросов в журнале (2026-10-31, М8, Ф1.6.7в)

| Где | Ошибка драйвера | Что выбрасывается |
|---|---|---|
| `Database.__init__` (открытие и `upgrade_database`) | `sqlalchemy.exc.DatabaseError`, `sqlite3.Error` (резервная копия — backup-API мимо SQLAlchemy) | `DatabaseConnectionError(database_error_text(exc), details={база, операция}) from exc`; движок освобождается. `MigrationError` — как раньше |
| `session_scope` (блок и коммит) | `sqlalchemy.exc.IntegrityError` | `DbIntegrityError(что нарушено, details={таблица, операция, SQL}, original=exc.orig) from exc` — после отката; остальные — как есть |

* **Текст пользователю.** «Занята другой копией» / «нет доступа» / общий — одна функция
  `migrate.database_error_text` для `Database.__init__` и `startup_error_text` (раньше разбор
  жил только в окне запуска). `startup_error_text` на `DatabaseConnectionError` отдаёт её
  `detail` (без кода `[6002]`). Нарушение целостности — по сообщению SQLite
  (`_integrity_detail`: повтор уникального, пустое обязательное, внешний ключ, CHECK; поле —
  если SQLite его назвал); таблица и операция — из текста SQL (`_statement_target`).
* **Журнал** пишет `session_scope` — `log_text()` (подробности, исходная ошибка) с
  трассировкой; у исключения приложения из блока — тоже `log_text()`, у прочих — прежнее
  `Ошибка: <текст>`. Журнал пишется до `raise … from`, поэтому `original` у
  `DbIntegrityError` задаётся явно (`exc.orig`): цепочки в этот момент ещё нет (найдено
  тестом). Окно запуска (`interfaces/gui/gui_window/main.py`) пишет `log_text()` ошибки
  открытия.
* **Значения запросов** (ФИО, телефоны, тексты — личные данные) SQLAlchemy кладёт в текст
  своих ошибок (`[parameters: …]`), а с ним — в трассировку цепочки: убрать их только из
  `details` было бы мало. Поэтому движок создаётся с `hide_parameters=True`; для отладки —
  настройка `LOG_SQL_PARAMS` (`Database(log_sql_params=True)`, решение владельца
  2026-10-31): значения видны в ошибках и в `details['параметры']`, при открытии базы —
  предупреждение в журнал. Флаг задаётся движку при создании — его смена переоткрывает
  базу (`ConfigApplier.apply_database`, блок `database`); переключатель на экране — Ф2.2.7.
* Внешние ключи в основном движке не включены (`PRAGMA foreign_keys` — только в движке
  миграций, выключен): «нет связанной записи» сейчас не возникает, текст — на будущее.
* Тесты: `tests/test_database_shema/test_database_errors.py` (на коде до правки 22 из 24
  падают), `tests/test_config/test_manager_behavior.py` (флаг: `apply_database`, `get_db`).

## 8. Автомиграции (2026-10-18)

Три части; опасные изменения (переименование, смена типа, перенос данных) — всегда вручную:
автоматика видит переименование как «удалить + добавить» и потеряла бы данные.

| Часть | Где | Что делает |
|---|---|---|
| **Применение** | каждый запуск (`Database.__init__` → `upgrade_database`) | недостающие миграции, копия, блокировка, откат при сбое (§2) |
| **Автодостройка** | каждый запуск, после миграций (`MigrationSettings.repair_drift`, по умолчанию да) | база сравнивается со схемой ПОСЛЕДНЕЙ миграции (`schema_at(head)`, собирается в памяти один раз за процесс): недостающее безопасное — таблица, необязательный столбец, индекс — дописывается (копия `…-<версия>-repair`); лишнее не трогается (запись в журнал уровня DEBUG — иначе повторялась бы при каждом запуске); нет обязательного столбца — отказ. Тот же механизм, что для старых баз (§3), только образец — последняя схема |
| **Генерация миграции** | запуск из исходников (`main_gui_window.py` → `configure(autogenerate=True)`), сборка | модели сравниваются со схемой последней миграции в памяти (`pending_model_changes`); только безопасные добавления → файл `versions/<NNNN>_auto_<дата_время>.py` с описанием (`generate_migration`), затем он применяется как обычная миграция; небезопасные — отказ «напишите миграцию вручную» (окно запуска покажет) |
| **Проверка сборки** | `scripts/build_win.py` перед PyInstaller | `python -m app.database.migrate check --generate`: одна «голова», модели = миграции; безопасные отличия → файл миграции и ОСТАНОВКА сборки (просмотреть, добавить в git, собрать снова); код 0 — всё в порядке |

* **В exe генерации нет**: файлы миграций там во временной папке (`_MEI…`) и пропали бы;
  совпадение моделей и миграций гарантирует проверка при сборке.
* **В тестах генерации нет** (по умолчанию выключена): тесты регистрируют свои модели на общей
  `Base` — иначе тест создал бы файл миграции в настоящей папке `versions`. Тесты подменяют
  модели через `migrate._default_metadata`.
* **Номер автомиграции** с датой и временем — две ветки разработки не получат одинаковый;
  если обе добавили миграции — две «головы», запуск и сборка остановятся (нужен `alembic merge heads`).
* **Стоимость** автодостройки при запуске — ~16 мс на базе проекта (без неё ~1 мс): сборка
  схемы в памяти один раз и сравнение. Растёт с числом таблиц и миграций; отключается
  `configure(repair_drift=False)`.
* Автомиграция, созданная при запуске из исходников, — обычный файл: его нужно просмотреть
  и добавить в git (в журнал пишется предупреждение с путём).
* **Что считается безопасным** (`is_safe_addition`, `unsafe_changes`): новая таблица (с её
  индексами и связями); необязательный столбец или столбец со значением по умолчанию;
  обычный индекс; связь, все столбцы которой новые. **Небезопасно:** удаление, смена типа
  или обязательности, связь на существующий столбец, уникальный индекс на существующей
  таблице (A4: повторы в данных клиники уронили бы миграцию).
* **Автодостройка не роняет запуск** (A5): каждый пункт — в своей точке отката; пункт,
  который не удаётся дописать, пропускается с предупреждением в журнал (при каждом
  запуске — пока причину не устранят). Отказ — только при нехватке обязательного столбца:
  без него программа всё равно не работала бы.
* Удалили файл автомиграции, уже применённой к базе разработчика, — база «новее программы»
  (M9): вернуть базу из резервной копии `.bak-…` рядом с ней.
* Две копии программы из исходников с одновременно изменёнными моделями создадут две
  автомиграции — две «головы»; следующий запуск остановится с понятным сообщением.

## 7. Журнал проверок

| Проход | Что |
|---|---|
| 0 (разработка) | M1 — откат DDL при сбое (отдельный движок с транзакциями); M2 — имена столбцов в описании отличий; `Column.copy()` устарел — новый столбец; `create_tables` (не `init_db`) |
| 1 | M3 — две копии программы одновременно на одной базе: обе меняли её параллельно, вторая падала («таблица уже есть»). Теперь `BEGIN IMMEDIATE` (блокировка записи сразу) и решение — по версии, прочитанной ПОД блокировкой; обычный случай (база свежая) — без блокировки. M4 — последняя версия миграций запоминается (раньше папка миграций читалась при каждом открытии `Database`). M5 — описание исходной миграции («не менять: на неё опираются все базы»). Тесты: одновременный запуск на новой и старой базе (падают на коде до исправления); проверка на копии боевой базы повторена |
| 2 | Сценарий «вышла следующая миграция» (тестовая 0002 во временной копии папки миграций: новый столбец + пересборка таблицы SQLite): на базе 0001, на старой базе, на новой, откат вниз; сбой в конце 0002 — откат ВСЕГО (пересборка таблицы тоже), база на 0001, данные целы. **M6** — старая база + дальнейшая миграция давали ДВЕ одинаковые копии (`-legacy` и `-0001_baseline`): до фиксации транзакции файл тот же. Теперь одна. Консольный путь (`alembic -c … upgrade/check`) проверен во временной папке |
| 3 | **M7** — ошибка открытия базы при запуске (отказ миграции, база занята другой копией, нет прав) вылетала необработанной: exe без консоли молча закрывался.
