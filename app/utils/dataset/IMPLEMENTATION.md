# Наборы данных (DataSet / DataSource) — проект

> Статус: ядро, Qt, слой приложения и пилотный экран написаны (2026-10-18, ветка
> `rework-dataset`); проверочные проходы 1–9 — до чистого (2026-10-18); сверка модуля —
> заход М3 (2026-10-25, ветка `rework-w1-dataset`, журнал §7). Доработки для новых экранов
> (`_dev/ПЛАН.md` §7: Д3, Д4, Д5, Д10, Д11) — в заходе М21.
> Решения владельца (2026-10-18): ядро ни с чем напрямую не связано — ни с черновиками, ни с
> какой-либо БД; `post()` по умолчанию пишет сразу в хранилище, черновики подключаются мостом
> в слое приложения; загрузка — параметр (всё сразу / порциями, размер порции настраивается);
> пилотный экран — пациенты → приёмы → фото.
> Идея — слой работы с данными в духе RAD Studio (Delphi/C++Builder, FireDAC), но
> независимый: переносится в другие проекты, где может не быть ни SQLAlchemy, ни Qt.

## 1. Что берём из RAD Studio и что — нет

| RAD Studio | Здесь | Примечание |
|---|---|---|
| `TFDConnection` | **источник хранилища** — объект, реализующий `DataBackend` | соединение — забота источника, ядро о нём не знает |
| `TFDTable` / `TFDQuery` | `DataSet` + источник «таблица» или «запрос» | запрос — именованный, параметры — значения, не текст SQL в форме |
| `TField` (подпись, видимость, только чтение, вычисляемое, подстановка) | `FieldDef` | описание полей — одно на набор; для приложения строится из `field_configs` |
| `CachedUpdates` / `ApplyUpdates` | черновики `app.utils.drafts` | уже есть: ветки, области сохранения, отмена/повтор, одна транзакция |
| `TDataSource` | `DataSource` | посредник между набором и экраном: извещения, «пауза» обновлений |
| `MasterSource` / `MasterFields` | `MasterDetailLink` | поле связи — из описания полей (внешний ключ) |
| `TDBGrid`, `TDBEdit`, `TDBNavigator`, `TDBImage` | пакет `dataset_qt` | отдельно от ядра |
| `LiveBindings` | `bind(виджет, источник, поле)` | одна функция на тип виджета |

**Не берём** (слабые места RAD): SQL в формах; общую на программу «текущую строку»
(у каждого набора — своя); логику в обработчиках форм (она в наборе — тестируется без
окна); работу только по одной строке (выделение нескольких строк — через черновики).

(чтение) и, если нужно, свой `DataWriter` (запись) и подключает их.

## 3. Ядро

### 3.1. Источник (`DataBackend`)

```python
class DataBackend(Protocol):
    def fields(self) -> Sequence[FieldDef]: ...            # описание полей (может быть пустым — тогда из набора)
    def key_field(self) -> str: ...                         # 'id'
    def fetch(self, query: Query) -> Page: ...              # Page(rows: list[dict], total: int | None)
    def get(self, key) -> Optional[dict]: ...               # одна строка (подстановки, обновление строки)
    capabilities: Capabilities                              # filter/sort/count/write — что умеет сам
```

Запись — отдельно от чтения (решение 2026-10-18): набор зовёт **способ записи**
(`DataWriter`: `insert/update/delete`). По умолчанию `DirectWriter` — сразу в источник
(`WritableBackend`). Отложенное сохранение (черновики) — свой `DataWriter` в слое
приложения; если ему нужно показывать не сохранённое поверх прочитанного и подсвечивать
строки — он реализует ещё `RowOverlay` (`overlay`, `row_status`). Ядро черновиков не знает.

Чего источник не умеет (`capabilities`), набор делает сам в памяти: сортирует, фильтрует
загруженное. Так `MemoryBackend` и простой REST-источник работают без лишнего кода.

### 3.2. Набор (`DataSet`)

* **Загрузка** — параметр `fetch_mode`: `ALL` (всё сразу) или `ON_DEMAND` (порциями по
  `fetch_size`, дальше — `fetch_more` при прокрутке; `last()`/`locate()` догружают сами).
* **Текущая строка** и **состояние**: `BROWSE` / `EDIT` / `INSERT` (+ `INACTIVE`).
  Навигация: `first/prior/next/last/move_to(i)/locate(ключ)`.
* **Правка**: `edit()` → значения в буфер → `post()` / `cancel()`; `insert()`/`append()`;
  `delete()`. Проверка полей (`required`, тип, свои проверки) — при `post()`.
* **Куда пишет `post()`** — в способ записи (`DataWriter`); по умолчанию — сразу в
  хранилище. Уход со строки во время правки сохраняет её (`auto_post`) или отказывает.
* **Вычисляемые поля** — функция от строки; **подстановки** — через `lookup.py`.
* **Фильтр и сортировка** — `set_filter(...)`, `set_order(...)` → перечитать окно.
* Ключ записи, а не номер строки, — «якорь» текущей строки: после перечитывания курсор
  возвращается на ту же запись, если она осталась.

### 3.3. События

Без Qt: подписка функцией. Виды: `opened`, `closed`, `refreshed` (окно перечитано),
`rows_inserted`/`rows_removed` (добавились строки окна), `row_changed(i, поля)`,
`current_changed(старая, новая)`, `state_changed`, `error`. `DataSource.disable()` —
пауза извещений (массовая правка без перерисовки), `enable()` — одно `refreshed`.

### 3.4. Главная → подчинённая

```python
appointments.link_master(patients_source)          # поле связи — из FieldDef (ссылка на patients)
```
Сменилась текущая строка пациентов — приёмы перечитываются с условием
`patient_id = текущий.id`. Новый пациент (ещё в черновике, id < 0) — приёмы пустые, но
добавлять можно: черновики уже связывают ребёнка с несохранённым родителем.

## 4. Как это ляжет на приложение

* `ServiceBackend` — поверх `get_page_filtered` (фильтры, сортировка, окно, количество),
  `get_by_id`; запись — существующий `ServiceAdapter` черновиков (одна транзакция).
* `FieldDef` строятся из `field_configs` (подписи, видимость, `compute`, заметки,
  подстановки по `eager_load`) — второй раз поля не описываем.
* «Одно описание таблицы» (следующий шаг после ядра): из одного описания — модель,
  DTO, `field_configs` и `FieldDef`; с автомиграциями новая таблица — это одно описание.
* Экраны: сначала одна пилотная пара «пациенты → приёмы» на новом слое рядом со старой
  (как делали с черновиками), затем остальные.

## 6. Ограничения ядра

* Условия и сортировка — по хранимым полям (их выполняет источник); по вычисляемым и
  подстановкам — нет.
* `append()` добавляет в конец ЗАГРУЖЕННЫХ строк, без догрузки остального (в RAD Studio
  `Append` уходит в конец набора; здесь это стоило бы загрузки всей таблицы).
* `total` — число строк по словам источника; новые, ещё не сохранённые строки (способ
  записи с `RowOverlay`) в нём не учтены.
* Сдвиги при догрузке: повторы по ключу отбрасываются, свои удаления учитываются в
  смещении (только строки, полученные от источника, — не новые строки способа записи,
  DS3); строки, удалённые в хранилище ДРУГИМИ, могут сдвинуть порцию на одну строку
  (обновление — `refresh()`).
* Ошибка источника при перечитывании — набор остаётся как был (строки, текущая строка,
  условия; DS6), событие `ERROR`, исключение — дальше.
* Итог по подчинённым, который считает программа (`AggregateDef`), читает из хранилища
  подчинённые строки главных строк окна (`поле_связи IN …`) и условия `where` — по
  хранимым значениям. Поэтому не видит строку, которую черновик ПЕРЕНЁС к главной строке
  окна от главной строки вне окна, и строку, которая начала отвечать `where` только в черновике (обратное —
  перенесённую от главной строки и переставшую отвечать `where` — учитывает, DS5).

## 8. Вычисляемые и свои столбцы (2026-10-18, ветка `rework-table-spec`)

Решения владельца: нужны и отметки строк (галочки), и итоги по подчинённым (число фото,
чеки об оплате); способ подсчёта итога — на выбор в описании столбца (программа / база).

| Вид | В описании | Значение | Правка | Сортировка |
|---|---|---|---|---|
| хранимое | обычный `FieldDef` | из хранилища | да | источник |
| от хранилища | `persistent=False` (в т. ч. итог, который считает база) | из хранилища | нет | источник (если умеет) |
| по своей строке | `calculated=функция` | в программе | нет | в памяти |
| подстановка | `lookup=LookupDef` | строка другой таблицы | нет | в памяти |
| своё поле набора | `local=True` | в наборе по ключу строки | сразу, без правки строки | в памяти |
| итог по подчинённым (считает программа) | шаг 2 | пачкой на окно + несохранённое | нет | в памяти |

**Свои поля (`local`, шаг 1).** Аналог `InternalCalc`: значение живёт в строке набора и
запоминается по ключу — переживает перечитывание, фильтр, догрузку; в хранилище не
пишется; меняется сразу (`set_local`, в т. ч. для любой строки — галочки в таблице), без
правки строки и проверок. `local_keys(поле)` — отмеченные (и незагруженные сейчас),
`clear_local`, `rekey` (временный id → настоящий: мост к черновикам зовёт сам; строку,
уже перечитанную с новым id, тоже обновляет). Сбрасываются при закрытии набора.

**Итоги по подчинённым, которые считает программа (`aggregate`, шаг 2).** `AggregateDef(child,
link_field, func=COUNT|SUM|MIN|MAX|AVG, field, where)`; `child` — набор (учитывается не
сохранённое его способа записи: новые строки считаются, помеченные на удаление — нет) или
источник (только хранилище). Считается пачкой на окно строк: один запрос
`поле_связи IN (ключи)`, ключи — кусками по 500 (предел параметров SQLite), затем
группировка; показ — из запомненного. Пересчёт: связь «главная → подчинённая» — после
сохранения/удаления в подчинённом (не во время ввода); `touch` (изменения извне, отмена/
повтор черновиков потомков) и `recalc` — вручную. Ошибка подсчёта при показе — в журнал и
«нет значения» (таблица не ломается). Второй способ — итог считает хранилище: обычное поле
`persistent=False` (как `has_photos` через `sql_compute`): сортировка по всей таблице, но
не сохранённое не видно.

**Сортировка по столбцам, которые считает программа (шаг 3).** `computed_by_program(поле)` —
по строке, подстановка, итог, своё поле. `sortable(поле)` — можно ли сейчас сортировать без
неверного порядка: поле от хранилища — всегда (сортирует источник); посчитанное
программой — только когда загружено всё (загрузка «всё сразу» или догружено всё).
`set_order` по такому полю сортирует в памяти по ВСЕМ строкам, источнику сортировка не
уходит; пока она действует, перечитывание загружает всё (порядок остаётся верным).
Загружено не всё — отказ с объяснением (а не молча неверный порядок по части строк).

**Qt (шаг 4).** Логические поля — галочкой в таблице (`CheckStateRole`); своё поле-отметка
ставится без смены текущей строки и без правки, в т. ч. в наборе «только для чтения» (то же —
в привязке `QCheckBox`). Щелчок по заголовку (`QTableView.setSortingEnabled`) — `sort()`:
по столбцу, который считает программа, только когда загружено всё (иначе — отказ с
объяснением и подсказка у заголовка). `build_form(источник, поля)` — форма по описанию полей:
виджет по типу (`extra['widget']`/`extra['choices']` — явно), подпись — `label`.

**Массовые действия (2026-10-18).** «Чек» — отметка строки для массовой работы (своё поле
набора). Механизм, а не набор: `Action` (подпись, обработчик `(набор, ключи, параметры)`,
доступность, подтверждение, какие параметры спросить, группа меню) и `ActionSet` (действия
таблицы, поле отметки, группировка `batch` — для черновиков `store.batch`: одно действие =
один шаг отмены; курсор после действия — на прежней записи). Встроенные: отметить все /
снять / обратить, задать значение поля, удалить отмеченные; своё — `actions.add(Action(...))`.
Qt — `ActionsMenu` (пункты по `can_run`, подтверждение и «поле — значение» окнами,
подменяемыми функциями), `FieldValueDialog`. В приложении — «Сохранить отмеченные» (через
черновики, с вопросами окна).
