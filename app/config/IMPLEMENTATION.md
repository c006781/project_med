## 1. Два уровня конфигурации

```
.env (python-dotenv)                 config.msgpack (MessagePack)
├─ APP_CONFIG_PATH  ── путь к ──▶    ├─ database_local_path, database_remote_path
└─ GITHUB_TOKEN (для обновлений)     ├─ YANDEX_TOKEN, PHOTOS_STORAGE_PATH, BACKUP_*
                                     └─ LOG_*, system_*, user_*, show_call_depth …
```

* `.env` — «загрузочный» уровень: где лежит основной конфиг, плюс токен GitHub.
* `config.msgpack` — все настройки приложения; его редактирует экран настроек.
  Если файла нет — значения по умолчанию из `AppConfigManager._defaults`, файл
  создаётся при первом `save()`.

### 1.1 Чтение

```
get_config_env(path=None)                         # manager.py — им пользуется всё приложение
└─ AppConfigManager.get_instance(config_path=path)
   ├─ path is None → _default_config_path()       # .env читается ОДИН раз (E6)
   │                 └─ _old_get_config_env()      # conf/get_config.py
   │                    ├─ get_getenv('APP_CONFIG_PATH', start_value='config.msgpack')
   │                    └─ get_getenv('GITHUB_TOKEN',   start_value='')
   │                       └─ get_dotenv_path() (E3) → load_dotenv()→ (ключа нет в файле) set_key()
   │                          → записанный ключ в os.environ (G1)
   └─ экземпляр по пути (Multiton, под блокировкой — M13) → manager.get_all() (копия)
```

(До 2026-10-15 схема показывала чтение .env при каждом вызове и `load_dotenv(override=True)`
после записи — см. D1, G1 в §6.)

### 1.2 Сохранение и применение (экран настроек)

С 2026-10-15 настройки применяет **только `ConfigApplier`** (решение владельца):

```
SettingsPage._save:
  old = manager.get_all().copy()                    # снимок ДО сохранения
  manager.set(...)…; manager.save()                 # атомарно; слушателей нет
  new = manager.get_all()
  applier = create_config_applier()                 # app.dependencies: ConfigApplier + ServiceHooks (К6)
  blocks = applier.apply_changes(old, new)          # только изменившиеся блоки
  main_window.on_settings_changed(blocks)           # обновление страниц/виджетов
  applier.errors → «Настройки сохранены частично»   # сбой блока не прерывает остальные (AP4)
```

* сервисы применитель получает обработчиками `ServiceHooks` от того, кто его создаёт
  (`app.dependencies.create_config_applier`); сам `app.config` не импортирует
  `app.dependencies` (К6, 2026-10-25);
* `database` — `reload_config()` у сервисов из кэша `dependencies` (те же объекты, что у
  страниц GUI; кэш не очищается);
* `photos` — новая папка в сервисе фото; `sync` — токен и пути в `SyncService`;
* `logging_*` — `AppLogger.configure(new)` (в т.ч. персональные `<имя>_LEVEL`, AP7);
  `backup` — только запись в лог.

Каждый блок применяется отдельно (`_run_block`): исключение → лог (файл `system`) и
`applier.errors[блок]`; остальные блоки применяются. Сбой одного сервиса при смене БД не
мешает перезагрузить остальные, но блок `database` попадает в `errors` (AP3/AP3a).
`cli apply_settings` печатает ошибки по блокам (CLI1).

`apply_*(new, old=None)`: без снимка — принудительно (CLI `apply_settings` после ручной
правки файла).

**Как было до 2026-10-15:** сервисы подписывались на `save()` и при ЛЮБОМ сохранении
переоткрывали БД; `ConfigApplier.apply_*` сравнивали с уже сохранённым менеджером и ничего
не делали. API слушателей (`add_change_listener`) оставлен — подписчиков в приложении нет.

## 4. Решения и детали

* **E1.** Возвращаемое значение не изменилось: пустое → значение по умолчанию.
  Изменилось условие ЗАПИСИ: дописывается только ключ, которого нет в самом файле
  (`_key_in_file`, через `dotenv_values`).
* **E2.** Ошибка записи/создания .env → предупреждение в stderr (`_report`), значение по
  умолчанию в памяти. Логгер не используется: .env читается до настройки логирования.
* **E3.** Где лежит .env — `get_dotenv_path()`: `$PROJECT_MED_ENV_DIR` → папка собранной
  программы (`sys.frozen` → папка exe/бинарника; Windows и Linux одинаково, «рабочая папка»
  ярлыка не важна) → папка запущенного скрипта (`__main__.__file__`) → текущая папка
  (интерактивный режим). Вверх не ищется (раньше `find_dotenv` мог взять чужой .env выше
  проекта). Следствия: `main_gui_window.py`/`main_cli.py`/`run.sh` → .env в корне проекта;
  модуль, запущенный напрямую для отладки, — свой .env рядом с модулем (боевой не трогается,
  как и задумано владельцем); под pytest папку задаёт `tests/conftest.py` (временная).
  Пути к БД, логам, фото и `APP_CONFIG_PATH` — настраиваемые, E3 их не меняет:
  относительные считаются от текущей папки «запущенного», как и раньше.
* **E6.** `AppConfigManager._default_config_path()`читает `APP_CONFIG_PATH` один раз;
  `reset_default_config_path()` — перечитать.
* **M1.** Битый файл или «не словарь» → `config.msgpack.broken-<ГГГГММДД_ЧЧММСС>` (при
  совпадении имени — `…-1`, `…-2`, M11), новый
  файл с умолчаниями, ERROR в лог; `broken_config_backup` / `broken_config_message` у
  менеджера; `MainWindow` показывает окно «Конфигурация восстановлена» и открывает
  настройки. Переименовать не удалось → новый файл НЕ пишется (битый не затирается).
* **M15.** Файл есть, но не читается (`OSError`: заблокирован, нет прав, это папка) — НЕ
  повреждение: файл не трогается, умолчания в памяти, `broken_config_message` (без
  `broken_config_backup`); окно «Конфигурация не загружена». `MainWindow` берёт текст
  сообщения сразу: экран настроек при входе вызывает `load()`, а он сбрасывает флаги (M10a).
* **M9/M10.** `load()` строит значения заново (умолчания + файл) и сбрасывает флаги
  битого файла — несохранённые изменения в памяти теряются (так и нужно экрану настроек).
* **M12/M12a.** `save()`: временный файл `<путь>.<pid>-<uuid>.tmp` рядом, `open(..., 'xb')`
  (права по umask), затем `os.replace`.
* **M13.** `AppConfigManager.get_instance()` — под `_instances_lock` (RLock).
* **G1.** Записанные в .env ключи кладутся в `os.environ` по одному; .env не
  перезагружается с `override=True` — переменные окружения системы важнее файла.
* **M3.** Слушатели-методы — `weakref.WeakMethod`; функции/лямбды — обычные ссылки.
