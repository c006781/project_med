## События таблиц и сборщик мусора (`ПЛАН.md` Ф1.6.7г, Ф1.6.7д, Ф1.6.10г, Ф1.6.10ж; В-19)

Разбор 2026-10-31 (по коду на `rework` 4cc8196).

**Серьёзные**

* **Р-1. Изменения мимо ORM не вызывают события.** Репозитории сейчас удаляют через
  `session.delete` (события сработают), но `query.delete()`, сырой SQL, миграции пройдут
  мимо: строка исчезнет, файл фото останется. Нужно правило «только через ORM» и тест,
  ищущий такие вызовы. Триггеры SQLite видят всё, но с файлами работать не умеют.
* **Р-2. Внешние ключи SQLite не проверяются** — `PRAGMA foreign_keys` нигде не
  включается (проверено 2026-10-31). База примет ссылку на удалённую заметку / фото; ошибка
  сборщика даст битую ссылку молча. Включить `foreign_keys=ON` — но сначала проверить старые
  данные на битые ссылки, иначе включение сломает сохранение.
* **Р-3. Прежние значения ссылок.** Сборщику нужно знать, на что запись ссылалась до
  правки: история изменений ORM есть только у загруженных объектов и только до сброса в
  базу (flush). Кандидатов собирать при сбросе, а не в `before_commit` — к коммиту история
  уже очищена; иначе сборщик молча ничего не найдёт.
* **Р-4. Каскады и порядок.** Удаление пациента ORM-каскадом удаляет приёмы и фото — у
  каждого свои события; сборщик, удаляя, сам порождает новые изменения и кандидатов. Нужен
  цикл до неподвижной точки с ограничением и явный порядок действий на одном месте.
  Решение владельца 2026-11-01 (по разбору предела): предел рабочих кругов = глубина цепочки
  таблиц «только используемые» по схеме + 1, вычисляется при открытии базы (у заметок — 2;
  круг сверх глубины — предупреждение, сверх предела — `TableEventError`); при превышении —
  **откат всей транзакции**. Порядок перед коммитом: сброс → действия «перед коммитом» один
  раз → сборщик последним → журнал закрыт; круги ссылок среди «только используемых» —
  ошибка при открытии базы (Р-20).
* **Р-5. После коммита откатить нельзя.** Строка удалена и закоммичена, а файл не удалился
  (занят, нет прав). Есть FD10 (файл остаётся, предупреждение, повтор) — хвосты досчитывает
  полная сверка по кнопке (Ф1.6.10г, Ф2.2.6).

**Средние**

* **Р-6. Скорость.** Индексов по полям ссылок на заметки нет (у пациента 2 поля, у приёма
  5; индексы есть только у `patient_id`, `appointment_id`, текста заметки — проверено
  2026-10-31): «ссылается ли кто-то на заметку» — 7 полных просмотров таблиц на кандидата
  при каждом сохранении. Нужны индексы (миграция) или один составной запрос.
* **Р-7. Переходный период.** Пока работают и `NoteService.cleanup_unused_note`, и
  сборщик — заметку удалят дважды (та же ошибка «не найдена» и откат, что исправлена в М15).
  Переключать одним шагом (Ф1.6.10ж вместе с Ф1.6.7г); сборщик пропускает уже удалённое.
* **Р-8. Регистрация обработчиков.** Один `Database` на приложение (ТД-6): обработчики —
  один раз на движок; при `reopen_db` — заново и без повторов (иначе действие выполнится
  дважды). Проверить тестом.
* **Р-9. Опечатка в имени действия** в описании таблицы обнаружится только при событии —
  проверять имена при запуске (описание ↔ реестр действий), с понятной ошибкой.
* **Р-10. Триггеры SQLite и миграции.** Пересборка таблицы (ТД-2, `recreate='always'`)
  удаляет её триггеры — миграция должна создавать их заново, иначе пропадут молча. ORM не
  знает, что триггер изменил данные: объекты в памяти устаревают.

**Мелкие (понятность)**

* **Р-11. Невидимые удаления.** Каждое автоматическое удаление — строкой в журнал (что,
  почему, какая транзакция); полная проверка по кнопке — сначала список «будет удалено»,
  потом подтверждение.
* **Р-12. Отказ в «перед…»** — исключением приложения (`AppException`) с понятным текстом,
  не сырой ошибкой SQLAlchemy; черновики откатывают всё сохранение (как `restrict`).
* **Р-13. Заметка, созданная отдельным шагом и не привязанная,** сборщиком не трогается
  (смотрит только затронутые ссылки) — останется до кнопки. Осознанно.
* **Р-14. Синхронизация с Яндекс.Диском** заменяет файл базы целиком — событий нет и не
  нужно; базу закрыть и переоткрыть (`ОСТАЛОСЬ.md` п. 5.9).

**Найдено разбором предела цикла сборщика (2026-11-01; синтетика SQLAlchemy 2.0.48 / SQLite
3.37.2, опыты О1–О10 — в отчёте сессии; решения — по ответу владельца)**

* **Р-15. Изменения после уборки.** `before_commit` SQLAlchemy вызывает один раз за коммит,
  затем сам досбрасывает сессию (до 100 раз) — кандидаты из изменений, сделанных после
  уборки (чужие слушатели `before_commit`, `after_flush*`), не проверяются и без очистки
  достаются следующей транзакции (О1).
* **Р-16. Журнал транзакции переживает `close()` без отката** — срабатывает только
  `after_transaction_end` (О9): «после коммита» следующей транзакции выполнилось бы для
  строк брошенной (удаление файла существующего фото). Касается журнала шага 2
  (`table_events.py`, df62515).
* **Р-17. Устаревшая обратная коллекция** (`AppointmentNote.appointments`): удаление заметки
  через ORM при загруженной коллекции обнуляет живую ссылку приёма, уже переведённого на
  другую заметку (О6). Перед удалением — `expire` коллекции.
* **Р-18. Точки сохранения** (`begin_nested`): `before_commit` / `after_commit` /
  `after_rollback` срабатывают и для них (О10) — «после коммита» выполнилось бы до коммита
  внешней транзакции. В `app` ORM-точек сохранения нет; то же касается обработчиков ТД-9.
* **Р-19. Повтор id без AUTOINCREMENT** ломает учёт «уже удалено» по id (О8). У таблиц
  клиники `sqlite_autoincrement=True`; риск — для новых таблиц и тестовых баз.
* **Р-20. Циклы среди таблиц «только используемые»** (самоссылка, A ↔ B): подсчёт ссылок
  их не собирает, глубина зависит от данных (О3). Полная проверка по кнопке для них —
  пометкой от корней, а не «строки без ссылок».
* **Р-21. Действие события строки меняет сессию:** SQLAlchemy молча сбрасывает изменения
  чужих объектов, новые вставляет после уборки (О5) — правило есть, проверки нет.
* **Р-22. Вложенный `session_scope` без передачи сессии** коммитит и закрывает внешнюю
  транзакцию (общая `scoped_session`) — уборка срабатывает раньше времени.
* **Р-23. Двойное удаление удержанного объекта:** повторный `session.delete` проходит без
  ошибки, а события удаления срабатывают дважды (О7) — между кругами объекты не держать.

## Фото на ссылках (`ПЛАН.md` Ф1.6.7б, Ф1.6.10г; В-3)

Разбор 2026-11-01 (проект и шаг 1; синтетика SQLAlchemy 2.0 / SQLite 3.37.2).

* **Р-24. Порядок записи «файл → фото».** При включённых внешних ключах строка файла должна
  попасть в базу раньше фото. Без связи между моделями SQLAlchemy порядок вставки не
  гарантирует (синтетика: фото первым — `FOREIGN KEY constraint failed`). ✅ 2026-11-01 —
  связь `Photo.file` (описание: `column(..., references=, relation=)`), тест
  `test_file_row_written_before_photo_by_relation`.
* **Р-25. Удаление фото и файла одним сбросом** — порядок удаления по связи «многие к
  одному» без обратной коллекции не гарантирован (синтетика: файл удалялся первым — отказ
  внешнего ключа). В программе файл удаляет только сборщик — отдельным кругом после сброса
  удаления фото; удалять строку файла вручную вместе с фото нельзя.
* **Р-26. Создание фото мимо сервиса** (тесты, генератор тестовых данных, будущий код) без
  строки файла — отказ базы. ✅ 2026-11-01 — поправлены `temp_data_bd.py`, тест
  объединения; тесты на фикстуре `db_session` (без `PRAGMA foreign_keys`) не затронуты.
* **Р-27. Имя по времени** (`ГГГГММДД_ЧЧММСС`): несколько фото за секунду (выбор нескольких
  снимков) — одно имя; нужен номер `_2`… с проверкой и папки, и базы. Регистр имени на
  Windows не различается — имена только из цифр и `_`, расширение — как у исходника
  (`.JPG` и `.jpg` у двух файлов одной секунды — разные строки базы, один файл на диске:
  расширение приводить к нижнему регистру). Шаг 2. ✅ 2026-11-01 — номер `_2`… по папке и базе,
  файл создаётся только новым (`open(…, 'xb')`), расширение строчными (`_store_new_file`, тесты
  `test_photo_links.py`).
* **Р-28. Сверка в общей папке** без подпапки: в папке фото могут лежать чужие файлы —
  сверка трогает только имена нашего вида и старые `app_*`. Гонка с добавлением фото в
  другой транзакции: свежие файлы (моложе 10 мин) не трогать. Шаг 4. ✅ 2026-11-01 —
  `check_storage` / `clean_storage` (только `PHOTO_NAME_RE` и `app_*`, порог `STORAGE_MIN_AGE`;
  время изменения копии — время добавления, `test_photo_storage_check.py`).
* **Р-29. Пути Windows в старых данных** (`app_1\x.jpg`): строки файлов после миграции 0002
  хранят путь как есть; перенос в общую папку (шаг 3) приводит к одному имени без папки.
  ✅ 2026-11-01 — `photo_file_path` понимает `\` на любой системе; перенос даёт имя по времени
  (`test_photo_relocate.py`).
* **Р-30. Удаление перенесённой записи черновиками (Ф1.6.3б, В-21) и правило «черновики сами не
  удаляют»** (В-18, В-19). Здесь удаление следует из явных действий пользователя (перенёс, потом
  удалил), а не из правила ссылок, поэтому не считается нарушением, но граница тонкая: нельзя удалить
  запись, если перенос сделан не пользователем (объединение, импорт). Учесть: «сохранили только
  новую запись» — поглощение остаётся; отмена новой записи возвращает к прежнему родителю (ОСТ п. 5.6);
  удаление файла — только действием таблицы файлов и только с последней ссылкой; значение правила —
  параметр, а не ветвление по всему коду; предупреждение до сохранения должно называть, что будет
  удалено. На копии проверить откат транзакции: фото и файл остаются.
  ✅ 2026-11-07 (DR10) — поглощение при сохранении только новой записи и возврат при отмене сохранены; файл — только действием таблицы файлов, с последней ссылкой; значение — один параметр; предупреждение называет запись и прежнего родителя; перенос не пользователем — признак `moved_by_user` и сверка родителя в транзакции; откат проверен на временной базе (`test_moved_into_deleted_new.py`).
