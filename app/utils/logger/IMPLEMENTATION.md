## 1. Что делает модуль

Обёртка над стандартным `logging`, которая добавляет:

1. **Реестр именованных логгеров (Multiton).** `AppLogger.get_instance('имя')` возвращает
   один и тот же объект для одного имени. Реестр свой у каждого класса (`_instances`).
2. **Указатель на место вызова** в каждой строке: `File "...", line N, in <func>` — в формате,
   который IDE превращает в кликабельную ссылку.
3. **Декоратор `log_execution_time`** — пишет `[Начало]` / `[Завершение: X сек]` вокруг вызова.
   В приложении применён ~1300 раз.
4. **Режимы, переключаемые на лету:** логгер целиком, консоль, файл, уровень — по одному
   логгеру, по группе (префикс имени) или из конфига приложения.
5. **Общий файловый обработчик (мастер/слейв).** Много логгеров пишут в один файл через
   один `RotatingFileHandler`, чтобы ротация работала корректно.
6. **Восстановление файла лога**, если его удалили во время работы программы.
7. **Вывод в любую функцию** вида `print(text)`: Telegram-бот, окно программы, список —
   для одного логгера (`add_output`) или для всех (`add_global_output`), в том числе в
   фоновом потоке (§3.7).

Модуль **самостоятельный**: только стандартная библиотека, импорты внутри пакета
относительные. Его можно скопировать в другой проект — см. §8.

Формат строки:

```
2026-10-14 16:37:36,183	INFO	[ConfigApplier]	>> File "C:\...\config_applier.py", line 420, in <apply_logging>:	Применение новых настроек
<время>                 <ур.>	[<имя логгера>]	<отступ> <место вызова>:	<сообщение>
```

Отступ `>`…`>` — глубина вложенности вызовов (см. §5.4).

## 2. Как это используется в приложении

### 2.1 Типичный вызов

```python
@AppLogger.get_instance(
    name='ConfigApplier',
    enable_file_logging='system',   # строка = «бери настройки и файл у логгера system»
    use_name_in_filename=False,
).log_execution_time(level=AppLogger._parse_log_level('DEBUG'))
def apply_logging(self, new_config): ...
```

Статистика по коду (`app/`, `interfaces/`): `get_instance` — ~1400 вызовов,
`enable_file_logging='system'` — ~1200, `='user'` — ~80.

### 2.2 Последовательность старта GUI

После развязки с конфигом (2026-10-14):

1. `main_gui_window.py` импортирует `interfaces/gui/gui_window/main.py`, тот —
   `app.utils.logger.logger`. Импорт создаёт `system`, `user` и `main.py` **по
   умолчанию** (консоль, INFO, без файла) — конфиг не читается.
2. **`setup_logging()`** (`app/config/logging_setup.py`) читает конфиг и вызывает
   `AppLogger.configure(config)` → уже созданные логгеры перенастраиваются.
3. Вызов `main()` → первая запись `main [Начало]` уже идёт по настройкам из конфига.
4. Внутри `main()` импортируется `MainWindow` → создаются остальные логгеры; они берут
   конфиг из `configure()`, ничего не читая.
5. `MainWindow.__init__` вызывает `AppLogger.configure(config_manager.get_all())` ещё раз
   (страховка на случай запуска окна в обход точки входа).

Замер на копии реальных `config.msgpack` / `clinic.db` (offscreen, до показа окна):

| Показатель | До развязки | После |
|---|---|---|
| Время старта | 5,5 с | 4,8 с; 2,3 с после ускорения поиска места вызова (§5.5) |
| Логгеров | 142 | 142 |
| Вызовов `get_config_env()` за старт | 154 | 12 (остались в `dependencies.py`, `clinic.py`, страницах GUI) |
| Записей в `app.log` | ~4570 | ~4550 |
| Первая запись в файле | `main [Начало]` | `main [Начало]` |
| Разных файловых обработчиков на один `app.log` | 18 | 1 (после S1/S3, §3.6) |

Число записей между двумя прогонами одного и того же кода плавает на десятки
(таймеры и ленивая подгрузка таблиц), набор логгеров совпадает.

**Требование:** если в конфиге включено полное логирование, весь старт программы должен
попадать в лог — начиная с первой записи. Обеспечивается порядком вызова в точках входа
(§7.1) и закреплено тестами `test_logging_setup.py`
(`test_entry_points_call_setup_logging_before_work`, `test_full_startup_first_record_goes_to_file`).

## 3. Устройство

### 3.1 Классы

```
logging.Handler
└── RotatingFileHandler
    └── RobustRotatingFileHandler      # переоткрывает удалённый файл, ретраи при PermissionError

logging.Handler
└── CallableHandler                    # запись → функция вида print(text); фоновый режим

BaseAppLogger                          # вся логика, конфиг не знает
└── AppLogger                          # конфиг приложения приходит через configure()
```

`BaseAppLogger` **не наследуется** от `logging.Logger`, а держит его в `self.logger`
(`logging.getLogger(name)`, `propagate=False`). Важное следствие: `logging.Logger` глобален
для процесса и общий у всех экземпляров с одинаковым именем (см. §6, `force_new`).

### 3.2 Состояние

Классовое (общее для всех, живёт на `BaseAppLogger`, у наследников **не** своё):

| Атрибут | Что хранит |
|---|---|
| `_global_handlers` | Обработчики, добавляемые ко всем логгерам (окно логов в GUI) |
| `_disabled_loggers` | Имена, которым запрещено писать (точное совпадение, не префикс) |
| `_depth_local`, `_depth_context` | Глубина вложенности для декоратора (поток / asyncio) |
| `_watchdog_started` | Запущен ли фоновый поток проверки файлов |

Классовое, своё у каждого наследника: `_instances` (реестр).

Экземпляра: флаги `_enabled`, `_console_enabled`, `_file_enabled`, `_use_name_in_filename`,
`use_timestamp`, `log_args`, `_show_call_depth`; параметры `log_level`, `base_log_file`,
`log_max_bytes`, `log_backup_count`; обработчики `console_handler`, `file_handler`;
связи `_master_logger`, `_shared_slaves` (слабые ссылки), `_shared_handler`;
ссылки на родителя из аргументов `_enable_file_logging_ref`, `_use_name_in_filename_ref`.

### 3.3 Блокировки

| Лок | Уровень | Защищает |
|---|---|---|
| `_instances_lock` | класс | реестр |
| `_global_handlers_lock` | класс | список глобальных обработчиков |
| `_share_lock` | класс | связи мастер/слейв |
| `_handler_lock` | экземпляр | обработчики и флаги экземпляра |

Порядок захвата: `_share_lock` → `_handler_lock`; при захвате двух `_handler_lock`
сортировка по `id()` (`share_file_handler_with`). `_update_handlers()` нельзя вызывать,
удерживая `_handler_lock`, — он сам берёт его и затем `_share_lock`.

### 3.4 Чтение конфига

Конфиг — плоский словарь. Значение ключа `KEY` для логгера `name` ищется
`_get_config_with_inheritance()` в порядке:

1. `{name}_KEY` — персональный ключ (`system_LEVEL`, `ConfigApplier_file_enabled`);
2. **родитель** — мастер общего файла или логгер из `enable_file_logging='родитель'`;
   поиск повторяется рекурсивно уже для родителя (`system_KEY`, …);
3. `LOG_KEY`;
4. `KEY`;
5. значение по умолчанию.

Пункт 2 — то, на чём держится всё приложение: ~1200 логгеров не имеют своих ключей и через
`enable_file_logging='system'` читают `system_enabled`, `system_LEVEL` и т. д.

Ключи: `LEVEL`, `FILE` (или `DIR`), `MAX_BYTES`, `BACKUP_COUNT`, `ARGS`, `enabled`,
`console_enabled`, `file_enabled`, `use_name_in_filename`, `use_timestamp`, `show_call_depth`.
Обязательны (`_validate_config`): `LEVEL`, `FILE`, `MAX_BYTES`, `BACKUP_COUNT` — в любом из
вариантов `{name}_` / `LOG_` / без префикса. `LOG_DIR` проверку **не** проходит — его
переписывает в `LOG_FILE` только `AppLogger.get_default_config()`.

Булевы строки: `'true'`, `'1'`, `'yes'` (без учёта регистра) → `True`, всё остальное → `False`.

Регистр окончаний ключей важен: `system_level` логгер не прочитает. С 2026-10-14
(P8) такие ключи — и опечатки вроде `system_LEVLE` — дают `UserWarning` при
`reload_all_from_config()`/`configure()`. Допустимые окончания — `CONFIG_KEYS`.

### 3.5 Путь к файлу (`_get_log_file`)

| `LOG_FILE` | Результат |
|---|---|
| существующая папка | `<папка>/app.log` |
| оканчивается на `/` или `\` | `<папка>/app.log` |
| несуществующий путь на `.log` | этот файл |
| существующий файл | этот файл |
| иное несуществующее | считается папкой → `<путь>/app.log` |

`use_name_in_filename=True` → `<имя>.log`; `use_timestamp=True` → `_<YYYYmmdd_HHMMSS>` от
момента создания логгера.

### 3.6 Мастер / слейв (общий файловый обработчик)

Правило (с 2026-10-14): **один обработчик на файл**. Логгер, которому нужен файл,
не открывает свой, если этот файл уже открыт другим логгером, а подключается к нему —
становится слейвом: подменяет `file_handler` обработчиком мастера и регистрируется в
`master._shared_slaves` (слабые ссылки).

К кому подключаться (`_file_share_target()`, проверяется при каждом перестроении
обработчиков и при создании):

1. к родителю по ссылке `enable_file_logging='имя'`, если у него сейчас реально открыт
   тот же файл (`_ref_parent_for_sharing()`);
2. иначе — к любому логгеру, который сам владеет открытым обработчиком на тот же файл
   (`_same_file_owner()`). Так `user` и его «дети» пишут через обработчик `system`.

Подключение всегда к **корневому** владельцу (`share_file_handler_with` поднимается по
цепочке мастеров) — цепочек `gui → user → system` не бывает.

Что общее, а что своё:

| Общее (у мастера, копируется слейвам) | Своё у каждого логгера |
|---|---|
| файл, ротация (`MAX_BYTES`, `BACKUP_COUNT`), `use_timestamp`, форматтер, `log_args` | уровень, `enabled`, консоль, `file_enabled` |

* Общий обработчик **без порога** (`NOTSET`): каждый логгер фильтрует своим уровнем
  (`logging.Logger.setLevel`). Уровень ставится только своей консоли. Поэтому `system`
  пишет в общий файл DEBUG, а `user` — INFO (S3). Исключение: явный `set_file_level()`
  у общего обработчика действует на всех, кто через него пишет.
* `reconfigure()` у слейва: параметры файла (`_SHARED_FILE_PARAMS`) уходят мастеру,
  уровень и флаги меняются у самого слейва.
* Мастер пересоздал обработчик (смена пути, ротации, включения) → `_update_shared_slaves()`
  подменяет его у слейвов. Мастер закрыл файл → у слейвов обработчик отцепляется
  (связь остаётся); слейв, которому файл нужен, при своём перестроении отвязывается и
  открывает свой (S2).
* Слейв выключил себе файл или логгер целиком → общий обработчик у него отцепляется,
  но не закрывается.
* Явный `unshare_file_handler()` отключает автоподключение (`_allow_auto_share=False`):
  логгер дальше пишет через свой обработчик, перезагрузка конфига его не «приклеит» обратно.
* `turn_off_file_logging()` у мастера сначала явно отвязывает всех слейвов — каждый
  открывает свой обработчик по своим настройкам.

Связь также создаётся явно: `share_file_with='имя'`, `share_file_handler_with()`; и при
создании — автоматически, если `share_file_with` не передан и у другого логгера тот же
`base_log_file`.

### 3.7 Выводы-функции (`add_output`)

```python
log.add_output(print)                                      # сразу, в том же потоке
log.add_output(send_tg, level='ERROR', background=True,    # в фоновом потоке
               formatter='%(levelname)s: %(plain_message)s')
AppLogger.add_global_output(send_tg, level='CRITICAL')     # от всех логгеров
```

* `CallableHandler` — обычный `logging.Handler`: форматирует запись и вызывает
  `func(text)`. Можно использовать и без BaseAppLogger, с голым `logging`.
* Фильтрация: сначала уровень логгера, затем порог вывода `level`.
* Формат по умолчанию: у `add_output` — форматтер логгера (как в консоли/файле, меняется
  `set_formatter`), у `add_global_output` — `LOG_FORMAT`.
* `plain_message` — поле записи: текст сообщения без `[имя]` и места вызова. Методы
  логгера и декоратор кладут его через `extra`; для чужих записей `CallableHandler`
  подставляет `record.getMessage()`.
* `background=True`: очередь (`queue_size`, по умолчанию 1000) + поток-демон
  `LogOutput-<имя>`. Переполнение — запись отбрасывается, `dropped += 1`, без блокировки.
  `flush(timeout)` ждёт опустошения очереди; `close()` дожидается остатка
  (до `CLOSE_TIMEOUT` = 5 с) и останавливает поток.
* Исключение в функции → `handleError` (стандартный `--- Logging error ---` в stderr),
  программа и остальные выводы продолжают работать; фоновый поток не умирает.
* Повторный вход: запись, сделанная из самой функции (в том же потоке), ей не
  передаётся — без бесконечной рекурсии. Флаг — `threading.local`.
* Выводы логгера хранятся в `_outputs`; `_update_handlers()` их не трогает, поэтому они
  переживают любые перестроения. Снимаются `remove_output()`, `close()`, `_retire()`.
  У слейва выводы свои — с мастером не делятся.
* Глобальные выводы живут в `_global_handlers` (общие для всех наследников).
  `close()` логгера их снимает, но не закрывает (B7).

**Формат.** Вывод в функцию по умолчанию получает ту же строку, что консоль и файл
(время, уровень, `[имя]`, место вызова, текст). Другой формат — только явно (`formatter=`).

**Настройка в объявлении наследника** (с 2026-10-14, `__init_subclass__`):

```python
class BotLogger(AppLogger,
                console_output=send_tg,                      # «консоль» → функция
                outputs=[print, {'func': send_admin, 'level': 'ERROR', 'background': True}],
                log_format='%(asctime)s %(levelname)s %(message)s'):
    pass
```

* `console_output` / атрибут `CONSOLE_OUTPUT` — консольный обработчик становится
  `CallableHandler(func)`: флаги консоли, `console_level` работают как раньше.
* `outputs` / `OUTPUTS` — общие выводы класса: **один** обработчик на класс (создаётся при
  первом обращении, хранится у класса, где объявлен `OUTPUTS`; наследники без своего
  `OUTPUTS` используют те же). Подключаются в `_update_handlers` как глобальные.
  Закрываются `close_class_outputs()` и `close_all()`; `close()` логгера их не закрывает.
* `log_format` / `LOG_FORMAT` — формат консоли, файла и выводов.
* Наследник получает свой реестр `_instances` автоматически. Раньше без явного
  `_instances = {}` он делил реестр с родителем.

## 4. Связь с конфигом приложения

### 4.1 Сейчас (с 2026-10-14)

```
точка входа ─▶ app/config/logging_setup.setup_logging()
                 ├─▶ config_manager.get_config_env()   (читает msgpack/.env)
                 └─▶ AppLogger.configure(config)        (логгер только получает словарь)

ConfigApplier.apply_logging(new) ─▶ AppLogger.configure(new)
MainWindow.__init__              ─▶ AppLogger.configure(config_manager.get_all())
```

* Пакет `app.utils.logger` **не импортирует** `app.config` (проверяется тестами
  `test_app_logger.py::test_logger_package_does_not_import_config` и
  `test_import_logger_does_not_load_config`). Зависимость одна: config → logger.
* `AppLogger._app_config` — последний конфиг из `configure()`. `None` — не настроен;
  тогда `get_default_config()` строит конфиг из `UNCONFIGURED_APP_CONFIG`
  (`file_enabled=False`): консоль, INFO, без файла.
* `AppLogger.build_logger_config(app_config)` — бывшая логика `get_default_config()`:
  `LOG_DIR → LOG_FILE` с разделителем на конце, значения по умолчанию, проброс `system_*`/`user_*`.
* `configure()` передаёт в `reload_all_from_config()` сырой конфиг **плюс** результат
  `build_logger_config()`. Сырой — ради персональных ключей (`ConfigApplier_LEVEL`),
  нормализованный — чтобы `LOG_FILE` у созданных до и после настройки логгеров совпадал
  (от строкового равенства `base_log_file` зависит автопривязка к общему файлу).
* `reload_all_from_app_config()` оставлен для совместимости: переприменяет последний
  конфиг из `configure()`, сам ничего не читает.
* `system` и `user` создаются при первом `AppLogger.get_instance()` (P6, `DEFAULT_LOGGERS`),
  а не при импорте модуля.

Что осталось вне логгера (отдельные задачи модуля конфига):

* ~~`get_config_env()` каждый раз дергает `.env`; если ключ пустой (`GITHUB_TOKEN=''`),
  `get_getenv()` считает его отсутствующим и **перезаписывает `.env`**.~~ Исправлено в
  модуле конфига (E1, 2026-10-14, `app/config/IMPLEMENTATION.md`); загрузка всех ключей
  `.env` при каждом чтении — E5, `_dev/ПЛАН.md` Ф1.4.3.
* Менеджер конфига по-прежнему не логирует — чтение конфига происходит до `configure()`
  (следствие выбранного варианта, §7.1). Циклического импорта больше нет, так что
  логирование в нём можно вернуть; записи до `configure()` пойдут в консоль.

### 4.2 Как было до 2026-10-14 (история)

```
logger.py ──import──▶ config_manager.manager.get_config_env()
                         └─▶ conf.get_config.get_config_env() ──▶ getenv.get_getenv() ──▶ .env
```

* `AppLogger.get_default_config()` вызывал `get_config_env()` при **каждом** создании
  логгера (154 раза за старт GUI, каждый раз с чтением и возможной перезаписью `.env`).
* `reload_all_from_app_config()` сам читал конфиг и передавал сырой словарь
  (без `LOG_DIR → LOG_FILE`; работало, потому что `_init_config_load` умеет читать `DIR`).
* Импорт логгера = чтение конфига: старый код сохранён в комментариях в `logger.py`.

**Почему так было.** Коммит `b3ccbf4` «новая схема», март 2026: менеджер конфига
логировал через `AppLogger`, логгер читал конфиг → циклический импорт. Логирование в
менеджере конфига закомментировали (`manager.py`, блоки с `sys.modules[...]`), в `logger.py`
остались закомментированные варианты с той же защитой. Итог — зависимость только в
сторону logger → config, а менеджер конфига ничего не логирует.

## 6. Неочевидные места («углы»)

* **Свои кадры стека логгер узнаёт по `LOGGER_CODE_FILES`** (`_common.py`) — список
  `co_filename` всех модулей пакета (до разбиения на модули — `_THIS_CODE_FILENAME`, он
  оставлен для совместимости), а не по пути вида `app/utils/logger/base_logger.py`. Сравнение — по
  `frame.f_code.co_filename` (не `FrameInfo.filename`: `inspect` может подменить его путём
  к исходнику). Так модуль работает под любым именем, в любом проекте и в PyInstaller.
  Если наследник добавляет свои методы-обёртки над `info()` и т. п., их нужно добавить в
  `skip_patterns_modeles`, иначе местом вызова станет обёртка.
* **`effective_enable_file_logging()` — это аргумент конструктора, а не состояние.**
  Текущее состояние — `is_file_enabled()` / `_file_enabled`. Путаница этих двух была
  источником R2, R3, S1. После исправлений `effective_*` используется только как
  значение по умолчанию `file_enabled` при создании логгера; для решений «включён ли
  файл сейчас» — только `_file_enabled`.
* **У каждого `logging.Logger` есть постоянный `NullHandler`** (`_null_handler`, R6).
  `_update_handlers()` его не трогает, снимает только `close()`. В `logger.handlers` он
  виден — при подсчёте «настоящих» обработчиков его нужно исключать
  (`_has_output_handlers()`).
* **Сообщения логгера о самом себе в `__init__`** (ссылка на несуществующий логгер)
  идут в stderr напрямую: обработчиков ещё нет, а `NullHandler` их бы поглотил.
* **Уровни: фильтрует `logging.Logger`, а не файловый/глобальные обработчики** (S3).
  Файловый обработчик создаётся с `NOTSET`. Проверять «какой порог у файла» по
  `file_handler.level` бессмысленно — смотрите `get_level()`.
* **`reload_from_config()` перестраивает обработчики и тогда, когда флаги не менялись,
  но файл нужен, а обработчика нет** (`_file_output_missing()`): так слейв восстанавливает
  файл после того, как мастер свой закрыл.
* **Полная синхронизация (`sync_full_state`) задаётся мастером**: при ``True`` у мастера
  его ``enable``/``disable`` и консоль повторяют слейвы. Слейв по умолчанию наследует
  флаг; явный ``sync_full_state=False`` при создании слейва — отказ (S4).
* **Существующий логгер игнорирует новые аргументы `get_instance()`** (кроме попытки
  `share_file_with`). Первый вызов с этим именем определяет всё.
* **`setLevel()` меняет только `logging.Logger`**, а `log_level` / `get_level()` — нет.
  Через `reconfigure(level=...)` меняется всё. `set_group_level` идёт через `setLevel`.
* **Отдельные уровни консоли/файла живут до первого перестроения обработчиков**
  (любой `enable*/disable*/reconfigure` с флагами). В одном вызове `reconfigure()`
  с флагами они применяются после перестроения (R4) и сохраняются.
* **`disable()` не снимает глобальные обработчики**, но методы логгера проверяют `_enabled`,
  поэтому до них ничего не доходит.
* **Список отключённых — точное имя**, не префикс. Для префикса — `disable_group()`.
  Группы — это `str.startswith`, а не иерархия по точкам: `'gui.Table'` цепляет `'gui.TableX'`.
* **`log_args=None` в декораторе читается в момент вызова** (с 2026-10-14; раньше —
  при импорте модуля). Первый аргумент вырезается, если параметр называется ``self``
  или ``cls`` — функция, у которой первый параметр назван иначе, получит его в лог.
  Для `__init__` аргументы не пишутся никогда.
* **Декоратор не перехватывает `BaseException`**, но строку `[Завершение]` пишет из `finally`.
* **`StreamHandler` запоминает `sys.stderr` при создании.** Подмена потока позже (pytest
  `capsys`, перенаправление вывода) на уже созданные логгеры не действует.
* **Watchdog** (поток `LoggerWatchdog`, стартует при первом `get_instance`, один на класс)
  каждые 5 с вызывает `reopen_missing_files()` — пересоздаёт только удалённые файлы.
  `reopen_all_files()` (принудительно все) оставлен для ручных вызовов.
* **`RobustRotatingFileHandler` при `PermissionError`** делает `MAX_RETRIES` попыток с
  паузой `RETRY_DELAY` в потоке вызывающего (не больше 0,1 с) и печатает
  `подход N провал` в stderr. Пауза держит блокировку обработчика.
* **`close()` не делает логгер «мёртвым»**: методы продолжают работать, WARNING+ уходят в
  `logging.lastResort` (`close()` снимает и `NullHandler`). Глобальные обработчики `close()`
  снимает, но не закрывает (B7). `close_all()` чистит реестр, но не классовые списки.
* **`force_new=True`**: старый экземпляр «уходит в отставку» (`_retire`), но объект
  остаётся рабочим — его вызовы идут через обработчики нового (тот же `logging.Logger`).
  Если через файл старого мастера пишут слейвы, файл не закрывается, а новый экземпляр
  открывает свой — на файле временно два обработчика.
* **Уровень можно передавать числом** везде, где принимается строка (`'ERROR'` или
  `logging.ERROR`), — `_parse_log_level` / `_level_to_int`.
* **Реестры наследников раздельные**, а `_global_handlers` и `_disabled_loggers` — общие на всех.
* **Поиск места вызова** — проход по `f_back` (`sys._getframe`) с кэшем ответа «кадр
  логгера» по ``(класс, co_filename, co_name)`` в `_skip_cache`. Если наследник меняет
  `skip_patterns_modeles` во время работы, очистите `_skip_cache`. При
  `show_call_depth=True` стек обходится ещё раз целиком (глубина). Декоратор место
  вызова вычисляет один раз при декорировании.
* **Неиспользуемый код оставлен** (правило проекта — история решений):
  `_get_config_param`, `_convert_patterns_modeles_tips`, `_thec_patterns_modeles*`,
  классовый флаг `on/off/status_show_call_depth_global` — помечены в докстрингах.
* **Обоснованные исключения pyflakes** (сверка М2, 2026-10-25): 11 неиспользуемых импортов
  в `base_logger.py` (`asyncio`, `os`, `sys`, `warnings`, `inspect`, `wraps`,
  `RotatingFileHandler`, `queue`, `_NOT_FOUND`, `_STOP_OUTPUT`, `_level_to_int`) —
  заголовок модуля до разбиения; оставлены, чтобы пространство имён `base_logger` не
  менялось для кода, импортировавшего эти имена отсюда (в проекте сейчас никто не
  импортирует — проверено поиском). Пометка — комментарий над импортами. Остальные модули
  пакета — 0 замечаний.

## 7. Планы и решения

### 7.1 Развязка с конфигом — решение от 2026-10-14

Цель: `logger.py` не импортирует конфиг; конфиг передаётся логгеру снаружи.
Ограничение: при полном логировании старт программы должен логироваться целиком (§2.2).

Рассмотренные варианты:

* **Буфер старта** — до получения конфига записи копятся в памяти и после настройки
  проигрываются по реальным правилам. Гарантирует, что не теряется ничего, позволяет
  менеджеру конфига снова логировать. Отклонён: сложнее, а записей до чтения конфига
  сейчас нет (замер §2.2: первая запись — `main [Начало]`, после чтения конфига).
* **Порядок вызова** — выбран. Точки входа первым делом вызывают `setup_logging()`,
  который читает конфиг и передаёт его в `AppLogger.configure(config)`. До этого логгеры
  работают на безопасных настройках по умолчанию (консоль, без файла).

Следствия выбранного варианта:

* Записи, сделанные до `setup_logging()`, в полный лог не попадают. Поэтому вызов должен
  стоять **до** вызова `main()` / `start_cli()` и до любой работы.
* Менеджер конфига по-прежнему не логирует чтение конфига (оно происходит до настройки).
* Скрипты и тесты, не вызвавшие `setup_logging()`, пишут только в консоль и не создают
  `./logs/app.log`.

### 8.1 Только ядро

Скопируйте папку пакета под любым именем (с 2026-10-14 ядро — несколько модулей, одним
файлом его больше не перенести) и унаследуйтесь, задав конфиг по умолчанию:

```python
from corelog.base_logger import BaseAppLogger   # папка пакета, скопированная как corelog/

class Log(BaseAppLogger):                  # свой реестр создаётся автоматически
    @classmethod
    def get_default_config(cls):
        return {'LOG_LEVEL': 'INFO', 'LOG_FILE': 'logs/', 'LOG_MAX_BYTES': 10_000_000,
                'LOG_BACKUP_COUNT': 5, 'file_enabled': 'True'}

log = Log.get_instance('bot')
log.add_output(send_to_telegram, level='ERROR', background=True,
               formatter='%(levelname)s: %(plain_message)s')

@log.log_execution_time(description='обработка заказа')
def handle(order): ...
```

### 8.2 Весь пакет (ядро + AppLogger)

Скопируйте папку `app/utils/logger/` под любым именем (например, `mylogging/`).
`AppLogger` ждёт плоский словарь настроек через `configure()` — откуда его взять, решает
проект (файл, переменные окружения, БД):

```python
from mylogging import AppLogger

AppLogger.configure({'LOG_DIR': 'logs', 'LOG_LEVEL': 'INFO',
                     'system_LEVEL': 'DEBUG', 'system_console_enabled': 'False'})
log = AppLogger.get_instance('worker', enable_file_logging='system')
```

Ключи `system_*` / `user_*` и логгеры `system`/`user`, создаваемые при первом
`get_instance()` (`DEFAULT_LOGGERS`, P6), —
особенность этого приложения; в другом проекте можно пользоваться ими или завести свои
имена с ключами `{имя}_LEVEL`, `{имя}_file_enabled` и т. д. (§3.4).

### 8.3 Что принадлежит этому проекту, а не модулю

* `app/config/logging_setup.py` — чтение `config.msgpack` и вызов `configure()`;
* вызов `setup_logging()` в точках входа (`main_gui_window.py`, `main_cli.py`, `pars_start.py`);
* `ConfigApplier.apply_logging`, `MainWindow` (`configure()` после сохранения настроек).
