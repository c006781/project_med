# Логгер приложения — заметки о реализации

> Файл для разработчиков: что делает модуль, как он устроен внутри, где у него
> проблемы и неочевидные места, и почему он устроен именно так.
> Обновляется вместе с кодом. Последнее обновление: 2026-10-14 (ветка `refactor/logger`).

Связанные файлы:

| Файл | Назначение |
|---|---|
| [base_logger.py](base_logger.py) | `BaseAppLogger` — вся логика; `RobustRotatingFileHandler` — файловый обработчик |
| [logger.py](logger.py) | `AppLogger` — наследник, связанный с конфигом приложения; создаёт `system` и `user` при импорте |
| [\_\_init\_\_.py](__init__.py) | Экспортирует только `AppLogger` |

## 1. Что делает модуль

Обёртка над стандартным `logging`, которая добавляет:

1. **Реестр именованных логгеров (Multiton).** `AppLogger.get_instance('имя')` возвращает
   один и тот же объект для одного имени. Реестр свой у каждого класса (`_instances`).
2. **Указатель на место вызова** в каждой строке: `File "...", line N, in <func>` — в формате,
   который IDE превращает в кликабельную ссылку.
3. **Декоратор `log_execution_time`** — пишет `[Начало]` / `[Завершение: X сек]` вокруг вызова.
   В приложении применён ~1300 раз.
4. **Режимы, переключаемые на лету:** логгер целиком, консоль, файл, уровень — по одному
   логгеру, по группе (префикс имени) или из конфига приложения.
5. **Общий файловый обработчик (мастер/слейв).** Много логгеров пишут в один файл через
   один `RotatingFileHandler`, чтобы ротация работала корректно.
6. **Восстановление файла лога**, если его удалили во время работы программы.

Формат строки:

```
2026-10-14 16:37:36,183	INFO	[ConfigApplier]	>> File "C:\...\config_applier.py", line 420, in <apply_logging>:	Применение новых настроек
<время>                 <ур.>	[<имя логгера>]	<отступ> <место вызова>:	<сообщение>
```

Отступ `>`…`>` — глубина вложенности вызовов (см. §5.4).

## 2. Как это используется в приложении

### 2.1 Типичный вызов

```python
@AppLogger.get_instance(
    name='ConfigApplier',
    enable_file_logging='system',   # строка = «бери настройки и файл у логгера system»
    use_name_in_filename=False,
).log_execution_time(level=AppLogger._parse_log_level('DEBUG'))
def apply_logging(self, new_config): ...
```

Статистика по коду (`app/`, `interfaces/`): `get_instance` — ~1400 вызовов,
`enable_file_logging='system'` — ~1200, `='user'` — ~80.

### 2.2 Последовательность старта GUI (замер 2026-10-14)

1. `main_gui_window.py` импортирует `interfaces/gui/gui_window/main.py`,
   тот — `app.utils.logger.logger`.
2. **Импорт `logger.py`** создаёт логгеры `system` и `user`. Каждый читает конфиг
   через `get_config_env()`.
3. Вызов `main()` (сам обёрнут декоратором → первая запись `main [Начало]`).
4. Внутри `main()` импортируется `MainWindow` → подтягиваются сервисы, страницы, виджеты →
   создаются остальные логгеры. **Каждый новый логгер снова читает конфиг.**
5. `MainWindow.__init__` вызывает `AppLogger.reload_all_from_app_config()`.

Замер на копии реальных `config.msgpack` / `clinic.db` (offscreen, до показа окна):

| Показатель | Значение |
|---|---|
| Время старта | 5,5 с |
| Логгеров | 142 |
| Вызовов `get_config_env()` | 154 |
| Записей лога | 4487 |
| Разных файловых обработчиков на один `app.log` | 18 |

**Требование:** если в конфиге включено полное логирование, весь старт программы должен
попадать в лог — начиная с первой записи. Сейчас это выполняется только потому, что каждый
логгер при создании сам читает конфиг. Любая развязка с конфигом обязана сохранить это
свойство (см. §7).

## 3. Устройство

### 3.1 Классы

```
logging.Handler
└── RotatingFileHandler
    └── RobustRotatingFileHandler      # переоткрывает удалённый файл, ретраи при PermissionError

BaseAppLogger                          # вся логика, конфиг не знает
└── AppLogger                          # get_default_config() читает конфиг приложения
```

`BaseAppLogger` **не наследуется** от `logging.Logger`, а держит его в `self.logger`
(`logging.getLogger(name)`, `propagate=False`). Важное следствие: `logging.Logger` глобален
для процесса и общий у всех экземпляров с одинаковым именем (см. §6, `force_new`).

### 3.2 Состояние

Классовое (общее для всех, живёт на `BaseAppLogger`, у наследников **не** своё):

| Атрибут | Что хранит |
|---|---|
| `_global_handlers` | Обработчики, добавляемые ко всем логгерам (окно логов в GUI) |
| `_disabled_loggers` | Имена, которым запрещено писать (точное совпадение, не префикс) |
| `_depth_local`, `_depth_context` | Глубина вложенности для декоратора (поток / asyncio) |
| `_watchdog_started` | Запущен ли фоновый поток проверки файлов |

Классовое, своё у каждого наследника: `_instances` (реестр).

Экземпляра: флаги `_enabled`, `_console_enabled`, `_file_enabled`, `_use_name_in_filename`,
`use_timestamp`, `log_args`, `_show_call_depth`; параметры `log_level`, `base_log_file`,
`log_max_bytes`, `log_backup_count`; обработчики `console_handler`, `file_handler`;
связи `_master_logger`, `_shared_slaves` (слабые ссылки), `_shared_handler`;
ссылки на родителя из аргументов `_enable_file_logging_ref`, `_use_name_in_filename_ref`.

### 3.3 Блокировки

| Лок | Уровень | Защищает |
|---|---|---|
| `_instances_lock` | класс | реестр |
| `_global_handlers_lock` | класс | список глобальных обработчиков |
| `_share_lock` | класс | связи мастер/слейв |
| `_handler_lock` | экземпляр | обработчики и флаги экземпляра |

Порядок захвата: `_share_lock` → `_handler_lock`; при захвате двух `_handler_lock`
сортировка по `id()` (`share_file_handler_with`). `_update_handlers()` нельзя вызывать,
удерживая `_handler_lock`, — он сам берёт его и затем `_share_lock`.

### 3.4 Чтение конфига

Конфиг — плоский словарь. Значение ключа `KEY` для логгера `name` ищется
`_get_config_with_inheritance()` в порядке:

1. `{name}_KEY` — персональный ключ (`system_LEVEL`, `ConfigApplier_file_enabled`);
2. **родитель** — мастер общего файла или логгер из `enable_file_logging='родитель'`;
   поиск повторяется рекурсивно уже для родителя (`system_KEY`, …);
3. `LOG_KEY`;
4. `KEY`;
5. значение по умолчанию.

Пункт 2 — то, на чём держится всё приложение: ~1200 логгеров не имеют своих ключей и через
`enable_file_logging='system'` читают `system_enabled`, `system_LEVEL` и т. д.

Ключи: `LEVEL`, `FILE` (или `DIR`), `MAX_BYTES`, `BACKUP_COUNT`, `ARGS`, `enabled`,
`console_enabled`, `file_enabled`, `use_name_in_filename`, `use_timestamp`, `show_call_depth`.
Обязательны (`_validate_config`): `LEVEL`, `FILE`, `MAX_BYTES`, `BACKUP_COUNT` — в любом из
вариантов `{name}_` / `LOG_` / без префикса. `LOG_DIR` проверку **не** проходит — его
переписывает в `LOG_FILE` только `AppLogger.get_default_config()`.

Булевы строки: `'true'`, `'1'`, `'yes'` (без учёта регистра) → `True`, всё остальное → `False`.

### 3.5 Путь к файлу (`_get_log_file`)

| `LOG_FILE` | Результат |
|---|---|
| существующая папка | `<папка>/app.log` |
| оканчивается на `/` или `\` | `<папка>/app.log` |
| несуществующий путь на `.log` | этот файл |
| существующий файл | этот файл |
| иное несуществующее | считается папкой → `<путь>/app.log` |

`use_name_in_filename=True` → `<имя>.log`; `use_timestamp=True` → `_<YYYYmmdd_HHMMSS>` от
момента создания логгера.

### 3.6 Мастер / слейв

Слейв подменяет свой `file_handler` обработчиком мастера и регистрируется в
`master._shared_slaves`. При изменении мастера `_update_shared_slaves()` копирует слейвам
уровень, форматтер, параметры файла. `reconfigure()` у слейва **перенаправляется мастеру**.

Связь создаётся: `enable_file_logging='имя'`, `share_file_with='имя'`, явным
`share_file_handler_with()` или **автоматически** — если `share_file_with` не передан и у
другого логгера тот же `base_log_file` (так `user` привязывается к `system`).

## 4. Связь с конфигом приложения (текущая)

```
logger.py ──import──▶ config_manager.manager.get_config_env()
                         └─▶ conf.get_config.get_config_env() ──▶ getenv.get_getenv() ──▶ .env
```

* `AppLogger.get_default_config()` вызывает `get_config_env()` при **каждом** создании логгера.
* `get_config_env()` каждый раз дергает `.env`; если ключ пустой (`GITHUB_TOKEN=''`),
  `get_getenv()` считает его отсутствующим и **перезаписывает `.env`**.
* `reload_all_from_app_config()` передаёт в `reload_all_from_config` сырой конфиг
  приложения, а не результат `get_default_config()` (там нет преобразования `LOG_DIR → LOG_FILE`;
  работает, потому что `_init_config_load` умеет читать `DIR`).
* Модуль при импорте создаёт `system` и `user` — импорт логгера = чтение конфига.

**Почему так (история).** Коммит `b3ccbf4` «новая схема», март 2026: менеджер конфига
логировал через `AppLogger`, логгер читал конфиг → циклический импорт. Логирование в
менеджере конфига закомментировали (`manager.py`, блоки с `sys.modules[...]`), в `logger.py`
остались закомментированные варианты с той же защитой. Итог — зависимость только в
сторону logger → config, а менеджер конфига ничего не логирует.

## 6. Неочевидные места («углы»)

* **`effective_enable_file_logging()` — это аргумент конструктора, а не состояние.**
  Текущее состояние — `is_file_enabled()` / `_file_enabled`. Путаница этих двух — источник R2, R3, S1.
* **Мастер работает как мастер, только если создан с `enable_file_logging=True`.**
  Если файл у него включён только ключом конфига, слейвы к нему не привяжутся (S1).
* **Существующий логгер игнорирует новые аргументы `get_instance()`** (кроме попытки
  `share_file_with`). Первый вызов с этим именем определяет всё.
* **`setLevel()` меняет только `logging.Logger`**, а `log_level` / `get_level()` — нет.
  Через `reconfigure(level=...)` меняется всё. `set_group_level` идёт через `setLevel`.
* **Отдельные уровни консоли/файла живут до первого перестроения обработчиков**
  (любой `enable*/disable*/reconfigure` с флагами).
* **`disable()` не снимает глобальные обработчики**, но методы логгера проверяют `_enabled`,
  поэтому до них ничего не доходит.
* **Список отключённых — точное имя**, не префикс. Для префикса — `disable_group()`.
  Группы — это `str.startswith`, а не иерархия по точкам: `'gui.Table'` цепляет `'gui.TableX'`.
* **`log_args=None` в декораторе фиксируется в момент декорирования** (при импорте модуля),
  смена `LOG_ARGS` в настройках на уже задекорированные функции не влияет.
  `self` в аргументах методов не вырезается (`inspect.ismethod` на этапе декорирования всегда `False`).
  Для `__init__` аргументы не пишутся никогда.
* **Декоратор не перехватывает `BaseException`**, но строку `[Завершение]` пишет из `finally`.
* **`StreamHandler` запоминает `sys.stderr` при создании.** Подмена потока позже (pytest
  `capsys`, перенаправление вывода) на уже созданные логгеры не действует.
* **Watchdog** (поток `LoggerWatchdog`, стартует при первом `get_instance`) каждые 5 с вызывает
  `force_reopen()` у всех файловых обработчиков. `force_reopen()` закрывает поток, вызывает
  `_open()` и **выбрасывает результат** — файл пересоздаётся, поток остаётся `None` до
  следующей записи. Работает, но каждые 5 с — закрытие/открытие на каждый обработчик.
* **`RobustRotatingFileHandler` при `PermissionError`** делает 5 попыток с `sleep(0.2)`
  в потоке вызывающего (в GUI — подвисание до ~1 с) и печатает `подход N провал` в stdout.
* **`close()` не делает логгер «мёртвым»**: методы продолжают работать, WARNING+ уходят в
  `logging.lastResort`. `close_all()` чистит реестр, но не классовые списки.
* **Реестры наследников раздельные**, а `_global_handlers` и `_disabled_loggers` — общие на всех.
* **Каждая запись вызывает `inspect.stack()`** (поиск места вызова), а при
  `show_call_depth=True` — ещё раз. `inspect.stack()` читает исходники файлов — это дорого.
  Декоратор место вызова вычисляет один раз при декорировании — он дешевле.

## 7. Планы и решения

### 7.1 Развязка с конфигом — решение от 2026-10-14

Цель: `logger.py` не импортирует конфиг; конфиг передаётся логгеру снаружи.
Ограничение: при полном логировании старт программы должен логироваться целиком (§2.2).

Рассмотренные варианты:

* **Буфер старта** — до получения конфига записи копятся в памяти и после настройки
  проигрываются по реальным правилам. Гарантирует, что не теряется ничего, позволяет
  менеджеру конфига снова логировать. Отклонён: сложнее, а записей до чтения конфига
  сейчас нет (замер §2.2: первая запись — `main [Начало]`, после чтения конфига).
* **Порядок вызова** — выбран. Точки входа первым делом вызывают `setup_logging()`,
  который читает конфиг и передаёт его в `AppLogger.configure(config)`. До этого логгеры
  работают на безопасных настройках по умолчанию (консоль, без файла).

Следствия выбранного варианта:

* Записи, сделанные до `setup_logging()`, в полный лог не попадают. Поэтому вызов должен
  стоять **до** вызова `main()` / `start_cli()` и до любой работы.
* Менеджер конфига по-прежнему не логирует чтение конфига (оно происходит до настройки).
* Скрипты и тесты, не вызвавшие `setup_logging()`, пишут только в консоль и не создают
  `./logs/app.log`.

### 7.2 Порядок работ

1. ✅ Характеризующие тесты (этот набор).
2. Развязка с конфигом (§7.1).
3. Исправление режимов R1–R6, S1–S4.
4. Прочие баги B1–B5, D1.
5. Проход по коду `base_logger.py`: докстринги/типизация, упрощение — с сохранением
   объяснений из закомментированного кода (переносить «почему» сюда).
