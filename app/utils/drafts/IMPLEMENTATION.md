## 1. Как пользоваться

```python
from drafts import DraftStore, EntityType, SaveScope, TreeSchema, build_plan, execute_plan

schema = TreeSchema([
    EntityType('patient', label='Пациент'),
    EntityType('appointment', parent='patient', parent_field='patient_id', label='Приём'),
    EntityType('photo', parent='appointment', parent_field='appointment_id', label='Фото'),
])
store = DraftStore(schema, parent_resolver=lambda t, i: ...)   # resolver необязателен

# интерфейс записывает изменения
store.modify('appointment', 12, {'cost': 500}, original={'cost': 400}, parent_id=1)
photo = store.create('photo', {'path': 'a.jpg'}, parent_id=12)       # -> -1 (временный id)
store.delete('appointment', 13, parent_id=1)

# значки строк
store.status('patient', 1)            # 'child' / 'own' / 'both' / None
store.subscribe(on_event)             # DraftEvent: kind, node, affected (узел + предки)

# сохранение: цель × направления
plan = build_plan(store, targets=[('appointment', 12)], scope=SaveScope.BRANCH)
if plan.missing_new_ancestors:        # новые родители вне объёма — спросить
    plan = build_plan(store, [('appointment', 12)], SaveScope.BRANCH, include_new_ancestors=True)
if plan.deleted_branches:             # удаляемые ветки — подтвердить
    ...
result = execute_plan(store, plan, adapter)   # одна транзакция; result.id_map: временные -> настоящие
```

Ещё:

```python
store.undo(); store.redo()                      # отмена/повтор (шаг = операция или batch())
store.revert_field('appointment', 12, 'cost')   # отменить одно поле
store.counts()                                  # {'appointment': {'new': 1, 'modified': 2, 'deleted': 0}}
find_conflicts(plan, read=adapter.read)         # что поменяли в БД, пока лежал черновик
save_with_confirmation(store, adapter, targets, scope, ask_new, ask_delete)   # весь сценарий
```

Цель: один узел (строка), несколько узлов (выборка экрана) или `None` (всё). Направления —
`SaveScope.SELF | DESCENDANTS | ANCESTORS` в любых сочетаниях (`BRANCH`, `PATH`, `FULL` —
готовые). Те же цель и направления работают в `store.discard(...)` и `store.has_changes(...)`.

## 2. Устройство

**Узел** — `(тип, id)`. У новой записи id временный (по умолчанию -1, -2 …;
`temp_id_factory` — свой генератор, например UUID).

**Черновик** — новая запись (все поля), изменение существующей (только изменённые поля +
исходные значения) или пометка удаления (изменения сохраняются — `undelete` вернёт).

**Связи.** Хранилище держит `узел → id родителя` и индекс `родитель → дети`. Источники:
`parent_id` / поле внешнего ключа в черновике; `remember_parent` (интерфейс сообщает
родителя записи без черновика); `parent_resolver` (хранилище спрашивает само, ответ кешируется).
Изменение поля внешнего ключа = перенос записи к другому родителю (событие `reparented`,
затронуты и старые предки).
Поле связи изменено черновиком — родителя решает черновик: сведения снаружи
(`remember_parent`, `parent_id` в `modify`/`delete`) его не меняют (L1, DR2).

**Статусы не хранятся** — вычисляются по индексу: `own` (есть черновик), `child` (есть у
потомков), `both`. Счётчиков нет, поэтому им нечему расходиться (главная проблема старой
системы).

**События.** На каждое изменение — `DraftEvent(kind, node, affected)`; `affected` — узел и все
предки: интерфейс перерисовывает значки этих строк. `batch()` копит события и рассылает пачкой.
Ошибка подписчика пишется в лог (`logging.getLogger('…drafts.store')`) и не мешает остальным.

**История отмены.** Перед каждой внешней операцией (или `batch()`) — снимок черновиков и
связей; операция что-то изменила (выросла версия) — снимок в стек отмены. `undo/redo`
восстанавливают снимок и рассылают `restored` по изменившимся узлам (с прежними и новыми
предками). Связи, узнанные позже снимка, сохраняются; связи новых записей, которых в снимке
нет, забываются. После сохранения в БД история очищается (`apply_saved`). Глубина —
`history_limit` (по умолчанию 100, 0 — выключено).

**Отмена новой записи** отменяет её новых потомков; существующие записи, перенесённые в неё,
возвращаются к исходному родителю (если он известен), остальные их правки остаются (N2).

**Запись, перенесённая в новую, которую потом удалили** — §5.2.

**План** строится без БД: выбор узлов → политика удаления → перенесённые записи (§5.2) → новые
предки вне объёма → порядок.
Создание — сверху вниз (родитель раньше детей), удаление — снизу вверх.

**Исполнение.** Внутри `adapter.transaction()`: создание (в поле внешнего ключа — настоящий id
только что созданного родителя), изменения, удаления. Хранилище меняется только после
успешной транзакции (открытый `store.apply_saved` — им же пользуется свой исполнитель); при
ошибке черновики остаются как были. После успеха временные id заменяются настоящими — и у
оставшихся черновиков детей (событие `remapped`).

**Конфликты** (необязательно, до исполнения): `find_conflicts(plan, read)` сравнивает
исходные значения изменённых полей с текущими в хранилище данных; удалённая там запись —
конфликт без поля. Решает вызывающий.

## 3. Решения и почему

* **Только стандартная библиотека, относительные импорты** — пакет копируется в другой проект
  под любым именем (тест `test_package_works_when_copied_elsewhere`).
* **Снимки `Draft` неизменяемые** — внешний код не может испортить хранилище.
* **`MISSING` вместо `None`** — `None` значит «родителя нет», `MISSING` — «не сообщили».
* **Новые предки вне объёма не добавляются молча** — `missing_new_ancestors`, решение за
  пользователем (`include_new_ancestors=True`); добавляются только сами предки, без их других
  детей.
* **Политика удаления — объект** (`resolve(store, selected) -> DeleteResolution`): можно
  заменить, не трогая остальное.
* **Версия хранилища в плане** — план, построенный до изменения черновиков (например, пока
  открыт диалог), не исполняется: `StalePlanError`.
* **Отмена новой записи отменяет её потомков** — их родитель так и не появится.
* **Удаление в хранилище данных — с потомками** (каскад БД или адаптер): пакет знает только
  потомков, у которых есть черновики.

## 4. Углы и ограничения

* Не потокобезопасно (рассчитано на поток интерфейса).
* У типа один тип-родитель. Запись, привязанная к нескольким родителям, — несколько типов или
  расширение схемы (§6).
* Потомки, о которых хранилище не знает (нет черновика и не сообщены), не участвуют в
  `descendants` — для статусов это не важно (у них нет изменений).
* Без `parent_resolver` и `remember_parent` цепочка предков обрывается на первом неизвестном —
  значок не поднимется выше.
* N2 (✅ 2026-10-16): существующая запись, перенесённая в новую, при отмене новой
  возвращается к исходному родителю; целиком отменяется, только если исходный родитель
  неизвестен (не передавали `original`).
* История отмены хранит снимки целиком — для сотен черновиков это дёшево; для десятков
  тысяч стоит перейти на журнал обратных операций.
* Значения полей пакет не проверяет и не копирует глубоко: изменяемые объекты в данных
  (списки) лучше не менять после передачи.

## 5.1. Ссылки (не владение) — 2026-10-18

Кроме дерева «родитель → ребёнок» запись может ссылаться на запись другого типа, не владея
ею (приём → врач, приём → общий шаблон): `EntityType(references=[Reference(поле, тип)])`.
Черновики данные БД сами не удаляют и не меняют сверх отданных изменений (2026-11-01):
правило удаления цели одно — `restrict`; `on_delete='set_null'` / `'cascade'` и
`collect=True` — ошибка описания `SchemaError` (`Reference.check_rules`; до 2026-11-01 —
обнуление ссылок, каскад и «переиспользуемые данные», журнал §5).

| Что | Как |
|---|---|
| порядок записи | новая цель ссылки создаётся раньше ссылающейся (порядок — по зависимостям: родитель + цели ссылок; круг из новых записей — отказ) |
| новая цель вне объёма сохранения | как новый предок: `missing_new_ancestors` (вопрос «сохранить и её?») |
| временный id | заменяется в ссылках сохраняемых записей и в ссылках ОСТАЛЬНЫХ черновиков (`_remap`) |
| удаление цели, на которую ссылаются не удаляемые записи | отказ `DeleteBlocked` и откат ВСЕГО (`restrict` — единственное правило; ссылки не обнуляются, ссылающиеся не удаляются — 2026-11-01) |
| цель, на которую больше никто не ссылается | остаётся в БД: черновики её не удаляют (до 2026-11-01 — `collect=True`); ставшее ненужным убирает хранилище данных (сервис), позже — сборщик по событиям таблиц |
| несохранённый черновик ссылается на удаляемое | отказ до обращения к БД |
| цель ссылок уже убрана хранилищем данных в той же транзакции (сервис удалил ставшие ненужными общие данные) | считается удалённой, повторно не удаляется (нужен `read`; 2026-10-31) |

Правила проверяются ВНУТРИ транзакции сохранения, после правок (порядок: создание → правки
→ удаление): БД уже отражает итог — ссылку, снятую в той же правке, правило не видит.
Адаптеру нужны `referrers(тип, поле, ids, tx)` (и `read(тип, id, tx)` — чтобы узнать, что
цель уже убрана хранилищем; без `read` цель удаляется как обычно); схема без ссылок —
старые адаптеры работают как раньше; ссылки есть, а искать их адаптер не умеет — отказ (а
не удаление без проверки). Отказ DR7 (2026-10-25, `collect` без `read`) убран вместе с
`collect` (2026-11-01). Сообщение отказа — по подписям схемы:
«Нельзя удалить «Врач #5»: на неё ссылаются записи: «Приём #12»».

## 5.2. Запись, перенесённая в новую запись, которую потом удалили — 2026-11-07

Сценарий: фото из приёма 1 пользователь перенёс в новый приём 2, потом приём 2 удалил. Решение
владельца (В-21): последовательность законна, поэтому при сохранении фото удаляется; файл —
только действием таблицы файлов и только с последней ссылкой (черновики файлы не трогают:
`adapter.delete` → сервис → сборщик → действие после коммита; откат оставляет фото и файл).
Это не нарушает «черновики сами не удаляют» (В-18, В-19): удаление следует из явных действий
пользователя, а не из правила ссылок.

| Что сохраняют | `DELETE` | `KEEP` |
|---|---|---|
| всё | запись удалена (`moved_deletes`) | остаётся (`moved_kept`) |
| прежнего родителя или его предка с потомками | запись удалена; удалённая новая вне объёма остаётся черновиком | запись не в плане, черновик остаётся |
| саму запись (`SELF`) | запись удалена | `blocked`, как раньше |
| только новую запись | поглощение: остаётся (`moved_kept`) | остаётся (`moved_kept`) |
| прежнего родителя без потомков | запись не в плане | запись не в плане |

Отмена новой записи (`discard`) при любом значении возвращает запись к прежнему родителю с её
правками (N2).

**Значение — один параметр.** `DraftStore(moved_rule=...)`; читает его только
`plan._moved_to_delete`. По умолчанию пакета — `KEEP`: переносимый пакет ничего не удаляет, пока
вызывающий не выбрал это явно. Значение приложения — одна строка
`app.draft.integration.DEFAULT_MOVED_RULE`. Смена значения (`store.moved_rule = ...`) делает
построенный план устаревшим: пользователю показали другое.

**Почему не политика удаления.** `DeletePolicy.resolve(store, selected)` не знает цели и
направлений, а именно они отличают «сохранили ветку прежнего родителя» от «сохранили только
новую»; перенесённую запись от прежнего родителя `select_nodes` вообще не находит (она уже под
новым). Менять протокол — ломать свои политики; поэтому отдельный шаг плана после политики.
`moved_deletes` — не `deletes`: запись не помечена на удаление, а проверка F3 (удалять можно
только помеченное) остаётся без исключений для `deletes`.

**Перенос не пользователем.** Удалить можно, только если выполнены ВСЕ условия:

1. **Перенос сделан пользователем** — `Draft.moved_by_user`. Ставит `modify(by_user=True)`; по
   умолчанию `False`, поэтому код (объединение, импорт, любой будущий вызов) удалить запись не
   может, даже если забудет об этом подумать. Решает последний перенос; вернули поле связи или
   отменили перенос — признак снят. Входит в историю отмены. `remember_parent` и `parent_id` —
   сведения, а не перенос.
2. **Известно, откуда** — поле связи есть в `original`.
3. **Над записью до удалённой только новые записи** (`_is_user_move_into_deleted_new`). Встретилась
   существующая запись — правило не применяется: запись остаётся у прежнего родителя, как при
   отмене (N2). Перенос в СУЩЕСТВУЮЩУЮ удалённую запись — тоже прежнее поглощение: В-21 только про
   новую.
4. **В БД запись там, откуда её перенёс пользователь** — `_moved_still_in_place` внутри транзакции:
   объединение и импорт пишут в БД мимо черновиков, поэтому признака из п. 1 мало. Родитель другой —
   `PlanError` и откат всего сохранения (адаптер без `read` — тоже отказ): запись цела, черновики на
   месте; выход — отменить новую запись или перенос. Тихо пропускать нельзя: диалог уже обещал
   удаление. Записи уже нет — удалять нечего.

Настоящее объединение пациентов проверено тестом
(`test_services_real_merge_moved_photo_is_not_deleted`).

**Сообщение.** `SavePlan.needs_delete_confirmation` — вопрос `confirm_deletes` задаётся при любом
значении правила и когда удаляемых веток в плане нет; план перед записью сверяется и по
`moved_deletes` / `moved_kept`. Текст — `drafts_qt.describe_deletes`: что удалится, что останется,
откуда перенесено. Вызывающий без `confirm_deletes` (экран наборов данных) сохранить такой план не
может: `save_with_confirmation` вернёт `None`, запись молча не удаляется. `moved_kept` не называет запись, прежний родитель которой сам удаляется в этом
сохранении: «останется» было бы неправдой.

**Границы.** `RejectChildChangesPolicy` по-прежнему отказывает: перенесённая запись для неё —
изменение в удаляемой ветке. Проверка `restrict` общая с `deletes` (порядок удаления — ОСТ п. 5.15,
не проявляется: на фото и приёмы никто не ссылается, заметки черновики не удаляют).
