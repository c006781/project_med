## 1. Как устроено

```
AppUpdater.check_for_updates()
  └─ UpdateChecker (QThread): GET api.github.com/repos/<slug>/releases/latest
       └─ is_newer_version(APP_VERSION, tag) → update_available(tag, url) | no_update | check_error
окно: «Скачать и установить» → AppUpdater.apply_update_from_release(pending_release_data)
  └─ UpdateApplier.start()
       ├─ auto_update_unavailable_reason(ОС, собран?) → error ДО скачивания
       ├─ select_release_asset(assets, ОС) → нет файла → error
       ├─ release_asset_sha256(release, имя файла) → нет хеша → warning (журнал + сигнал), дальше
       └─ UpdateDownloader (QThread): <exe_dir>/MedicalApp_new_<t>.exe.part → проверка
          размера → file_sha256(.part) == хеш релиза? (нет → error, .part удаляется)
          → os.replace → UpdateApplier._apply_update()
            └─ build_windows_update_script → update.ps1 (ждёт выхода, удаляет старый exe,
               запускает новый с --rename-to <старое имя>) → выход из программы
            └─ Linux: _apply_update_linux → prepare_linux_update → update.sh → выход (раздел 1.3)
```

Логика без Qt — функции модуля: `normalize_version`, `parse_version`, `is_newer_version`,
`mask_token`, `github_headers`, `current_system`, `select_release_asset`, `update_file_name`,
`parse_release_hashes`, `release_asset_sha256`, `file_sha256`, `build_windows_update_script`,
`auto_update_unavailable_reason`. Справочники:
`ASSET_RULES`, `UPDATE_FILE_EXTENSIONS`, `AUTO_UPDATE_SYSTEMS`, `DOWNLOAD_CHUNK_SIZE`.
Linux (раздел 1.3): `get_install_root`, `linux_install_unavailable_reason`,
`validate_manifest_path`, `parse_linux_manifest`, `read_linux_manifest`, `safe_extract_tar`,
`check_unpacked_update`, `build_linux_update_script`, `prepare_linux_update`,
`launch_linux_update_script`, `pop_linux_update_failure`, `linux_backup_keep_settings`; `UpdateError`, `LinuxUpdatePlan`.

Сигналы предупреждений (2026-10-31): `UpdateApplier.warning(str)` →
`AppUpdater.download_warning(str)` — установка продолжается (сейчас: в описании релиза нет
хеша выбранного файла). Окно пока не подключает — предупреждение только в журнале.

### Хеш файла релиза (SHA-256)

* `release.yml`, задача `create-release`: после скачивания артефактов шаг «Compute SHA-256»
  пишет `release_hashes.md` — блок с выводом `sha256sum` (`<64 hex>  <имя файла>`, имена без
  пути); `softprops/action-gh-release@v2` берёт его в `body_path`, а с
  `generate_release_notes: true` ставит перед автоматическими заметками (body + notes).
* Программа: `UpdateChecker` уже получает весь JSON релиза (`body` в нём) →
  `AppUpdater.pending_release_data` → `UpdateApplier.start` ищет строку для имени выбранного
  файла (`release_asset_sha256`, без учёта регистра) → `UpdateDownloader(expected_sha256=…)`
  сверяет `.part` после проверки размера, ДО `os.replace`.
* Формат строки: как `sha256sum` — два пробела или ` *` (двоичный режим, так пишет
  `sha256sum` Git Bash); путь перед именем отбрасывается; повтор имени — действует первая
  строка.

### 1.1 Как добавить ОС

1. `ASSET_RULES[<ос>] = ((слова в имени,), (окончания,))` — выбор файла релиза.
2. `UPDATE_FILE_EXTENSIONS[<ос>]` — расширение скачанного файла.
3. Хеш — строка для имени файла новой ОС в `release.yml` (шаг «Compute SHA-256»).
4. Замена файла — ветка в `UpdateApplier._apply_update` (по образцу
   `build_windows_update_script` — отдельная функция-генератор скрипта) и ОС в
   `AUTO_UPDATE_SYSTEMS`.

Тест `test_u2_rules_cover_extensions` проверяет, что справочники согласованы.

### 1.2 Решения

| Решение | Почему |
|---|---|
| Версии сравниваются кортежами чисел, завершающие нули отбрасываются | `1.10 > 1.9`, `1.0 == 1.0.0`; непонятный номер (`1.0-beta`) — «обновления нет»: безопаснее, чем предложить откат |
| Проверка «можно ли установить» — до скачивания | Раньше из исходников и на Linux файл скачивался, а потом ошибка (на Linux — `AttributeError`) |
| Скачивание во временный `.part`, проверка `Content-Length` | Оборванное скачивание раньше давало «успех» и недокачанный exe запускался скриптом замены |
| Токен в журнале — `mask_token` | Раньше токен GitHub целиком писался в журнал (DEBUG) |
| `verify=False` для приватного репозитория оставлен | Без проверки на собранном exe нельзя убедиться, что с certifi `SSLEOFError` ушёл — ТЕХДОЛГ ТД-4 |
| Скрипт PowerShell — функция `build_windows_update_script` | Текст не изменился (тест сравнения со старым выводом при переносе); теперь проверяется тестами |
| Имена классов, сигналов, `UpdateChecker._parse_version` сохранены | Окно и `main_gui_window.py` менять не нужно; `_parse_version` вызывает `is_newer_version` |
| Прежний код — в комментарии внизу файла | Правило проекта |
| Хеш — в описании релиза, а не отдельным файлом релиза | Описание приходит в том же ответе API, что и список файлов (`UpdateChecker`), — второй запрос не нужен; отдельный `.sha256`-файл мог бы попасть под правила выбора файла ОС (`ASSET_RULES`) |
| Описание релиза получено по `urllib` с проверкой сертификата, файл — по `requests` | При токене (`verify=False`, ТД-4) хеш приходит по проверенному каналу — подмена файла при скачивании обнаружится сверкой |
| Релиз без хеша — предупредить и установить | Решение владельца 2026-10-31: старые релизы (до публикации хешей) должны ставиться; предупреждение — журнал и `download_warning` |
| Хеш считается по `.part` после скачивания (`file_sha256`), а не на лету | Проверяется ровно то, что лежит на диске и будет переименовано; файл читается порциями `DOWNLOAD_CHUNK_SIZE`, лишнее чтение ~100 МБ — доли секунды |
| `verify=False` при токене не менялся, добавлено предупреждение в журнал | Решение владельца 2026-10-31 (ТД-4: токен — только для тестирования); проверка на собранном exe — Ф3.5 |
| Ошибка сверки — `ValueError` в `UpdateDownloader.run` | Общая ветка `except` удаляет `.part` и шлёт `error(текст)` — установка не начинается |

### 1.3 Linux: замена кода из архива (Ф1.5.5, вариант А, 2026-11-07)

Программа ставится разархивированием в любую папку и работает из исходников (нет `sys.frozen`).
Корень установки — `get_install_root()`: родитель `app/`, вычисляется от модуля; путь нигде не
зашит.

```
UpdateApplier.start()
  ├─ linux_install_unavailable_reason → error ДО скачивания:
  │    собранный бинарник / .git (папка или файл) / нет метки или манифеста /
  │    .update_in_progress / нет прав на запись (установка и папки кода)
  └─ скачивание в <установка>/MedicalApp_new_<t>.tar.gz (сверка SHA-256, как раньше)
_apply_update_linux → prepare_linux_update (код ещё не меняется; ошибка — error, программа работает)
  ├─ убрать остатки .update_<число> → распаковать в .update_<t>/ (safe_extract_tar)
  ├─ файлы на диске == манифест (check_unpacked_update); версия в архиве новее текущей
  ├─ манифест установки; папки кода не ссылки; requirements.txt изменился?
  └─ update.sh (права 700) → архив удалён → launch (новый сеанс) → выход из программы
update.sh (после выхода, все пути относительные)
  ├─ ждёт PID (зомби = вышел); 120 с не вышла — отмена, ничего не менялось, .update_failed
  ├─ .update_in_progress (PID скрипта) + sync
  ├─ файлы старого и нового манифеста → backup_<версия>/ ; папки удалённых модулей — убрать, если пусты
  ├─ файлы нового манифеста из .update_<t>/ на место (mv -T) + sync
  ├─ requirements.txt изменился → venv_project_med/bin/python -m pip install -r requirements.txt
  ├─ убрать .update_<t>, .update_in_progress → run.sh (setsid + nohup) → удалить себя
  └─ ошибка на любом шаге замены → откат → .update_failed → run.sh прежней версии → удалить себя
```

**Манифест — пофайловый.** `build_linux.sh` пишет в архив `.medicalapp_manifest` (первая строка
`# medicalapp manifest v1`, дальше все файлы дистрибутива, включая метку и сам манифест) и метку
`.medicalapp_dist`. В `parsers/` установленной программы лежат `logs/` и `photos/`, в
`app/` — `__pycache__/` и, возможно, `MedicalAppUpdates/` (`download_update` пишет рядом с
`get_app_dir()`), в `interfaces/` — `__pycache__/`. Заменять папку целиком нельзя ни в одной из них:
заменяются только перечисленные файлы, всё остальное на диске не трогается и в `backup_` не едет.
Список кода не зашит в updater; updater знает только запреты (`validate_manifest_path`): данные
(`.env`, `*.db`, `*.msgpack`, `*.log`, `photos`, `logs`, `logs_parser`, `MedicalAppUpdates`), `venv_project_med`,
`.git`, `__pycache__`, служебное обновления (`.update_*`, `backup_*`, `update.sh`, `update.log`),
абсолютные пути, `..`. `build_linux.sh` такие файлы из сборки убирает: иначе отказ получили бы все
установки разом (тест настоящей сборки — `test_u27_build_produces_valid_update`).

**Что происходит с файлом кода, которого нет в новой версии** (удалённый модуль): он есть в манифесте
установленной версии и нет в новом — переносится в `backup_<версия>/` и из программы исчезает. Папка
такого модуля убирается, только если в ней не осталось ничего, кроме `__pycache__`; с данными —
остаётся вместе с ними. Лишний файл кода, которого нет ни в одном манифесте (положен вручную), не
трогается. При откате файл возвращается, пустая папка создаётся заново.

**Откат** повторяемый: файлы, которые есть в `backup_`, возвращаются на место поверх новых;
добавленные (`ADDED_PATHS`: их не было на диске) удаляются, если уже перенесены из `.update_`; пустой
`backup_` убирается. Прервался — можно запустить снова (тест `test_u20_recover_interrupted_twice`).
Не удался — `update.sh`, `.update_in_progress` и `backup_` остаются, перезапуска нет.

**Сбой посреди замены** (выключение, убитый процесс): остаётся `.update_in_progress`. `run.sh` при запуске
вызывает `update.sh --recover`: откат, затем обычный запуск прежней версии, причина — в
`.update_failed`. Скрипт ещё жив (PID из метки, в командной строке `update.sh`) — код 3, `run.sh` пишет
«не запущена» и выходит.

**pip.** `python -m pip`, а не `bin/pip`: у `bin/pip` в первой строке зашит путь, после
переименования папки установки он не запускается. Ошибка — откат кода; затем попытка `pip install -r`
прежнего файла (пакеты на месте — сеть не нужна; pip успел заменить часть пакетов — вернёт их, если есть
сеть; не вышло — запись в `update.log`, программа всё равно запускается, совет `./install.sh`).

**Экранирование.** Путь установки в текст скрипта не попадает: скрипт переходит в свою папку
(`${0%/*}`), дальше пути относительные. Пути и версии подставляются через `shlex.quote`. Пробел,
кириллица, кавычка, `$` в имени папки проверены вживую. Перед первым обновлением `install.sh` в папке с
`$` не проходит: `setup_prod.sh` использует `activate` и `pip` из PATH (раздел 4).

**Проверка запуска (2026-11-07, U29).** После `run.sh` скрипт `LINUX_START_CHECK_SEC` (60 с) следит за процессом.
Новая версия сама завершилась с ошибкой — откат кода, причина в `.update_failed`, запуск прежней версии. Работает или
закрыта штатно (код 0) — успех. Сигналы извне (129, 130, 143: закрыт сеанс, Ctrl+C, выключение) сбоем не считаются. Слежение
за процессом, а не метка от программы: медленная миграция базы не даёт ложного отката, окно править не нужно. Чего не
ловит: программа зависла, но жива; упала позже 60 с; `setsid` разветвился (тогда видим код 0 — считается успехом).
**Откат возвращает только код.** База, которую новая версия успела обновить, остаётся новой: прежняя версия откажется её
открывать с понятным сообщением (`_ensure_known_revision`), копия базы до миграции — `<база>.bak-…` рядом с файлом базы
(`app/database/migrate.py`); подсказка об этом есть в тексте `.update_failed`.

**Старые копии кода (2026-11-07, U30).** Чистятся только после успешного запуска. Настройки (`UPDATE_BACKUP_KEEP_MODE`,
`UPDATE_BACKUP_KEEP_COUNT`, `UPDATE_BACKUP_KEEP_DAYS`; экран настроек, виден только на Linux): `count` — оставить N новых
(умолчание, 3), `days` — удалить старше N дней (умолчание 30); возраст — по времени изменения папки. Только что созданная копия
остаётся всегда. Удаляются только папки вида `backup_<версия>[_<метка>]`, другие с похожим именем (`backup_photos`) не
трогаются и не считаются. Значения передаются в скрипт при подготовке обновления (`linux_backup_keep_settings`), неверные
заменяются умолчанием.

**Границы.** Вторая запущенная копия программы не
определяется. Программа завершается через `sys.exit`, как на Windows, без `closeEvent`. Первую
версию с автообновлением ставят вручную: у прежних нет метки и манифеста. Сообщения `run.sh` видны только в терминале.
