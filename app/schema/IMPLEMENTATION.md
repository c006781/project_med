# Описание таблиц (app/schema) — заметки о реализации

Одно описание таблицы (`TableDef`) → модель SQLAlchemy, DTO (Pydantic), `field_configs` и
набор данных экрана (`app/tables`). Раньше на таблицу было 4 места: модель, DTO, настройки
полей, описание набора — теперь одно.

## 1. Состав

| Файл | Что |
|---|---|
| `define.py` | `TableDef` и поля-построители: `key`, `column`, `note`, `fk`, `children`, `computed`, `timestamp`; `build_model`, `build_dto`, `build_config`; `rebuild_dtos` (ссылки DTO друг на друга по имени) |
| `extras.py` | свои столбцы набора (`mark`, `calc`, `total`) и настройки связей (`Link`, `ref`) — перенесены из `app/tables/spec.py` (там — повторный экспорт) |
| `clinic.py` | описания таблиц клиники `PATIENTS`, `APPOINTMENTS`, `PHOTOS`, `CLINIC_DEFS`; функции настроек (`patient_full_name`, `photo_count_text`, `photo_image`) |

## 2. Подключено (2026-10-19)

* `app/database/database_shema/clinic.py`: `Patient`, `Appointment`, `Photo` =
  `<ОПИСАНИЕ>.build_model(Base, {'__repr__': …}, module=__name__)`; прежние классы —
  комментарием. `__repr__` — как у прежних классов (их строки ждут лог и тест B1).
* `app/dto/dto_all.py`: `PatientDTO`, `AppointmentDTO`, `PhotoDTO` = `build_dto(module=…)` +
  `rebuild_dtos(...)`; прежние — комментарием.
* `app/dto/field_configs.py`: `PATIENT_CONFIG`, `APPOINTMENT_CONFIG`, `PHOTO_CONFIG` =
  `build_config()`; прежние — комментарием.
* `app/tables/clinic.py`: `CLINIC` = `table_spec(d)` для каждого из `CLINIC_DEFS` (модель,
  DTO, настройки — из их модулей по именам описания; сервис — `provider(d.service)`).
* Заметки (`AppointmentNote`, `AppointmentNoteDTO`, `NOTE_CONFIG`) — по-прежнему вручную:
  это общая таблица, на которую ссылаются поля `note(...)`.

## 3. Совпадение с прежним

`tests/test_schema/legacy_snapshot.py` — снимок написанных вручную моделей (столбцы, типы,
NOT NULL, ключи, комментарии столбцов и таблицы, `sqlite_autoincrement`, индексы, связи с
каскадами и `back_populates`), DTO (поля, типы, умолчания, описания, порядок) и настроек
(ключи, значения, порядок). Тест `test_clinic_defs.py` сравнивает со снимком и
сгенерированное на отдельной базе, и то, что использует приложение. Поэтому схема для
Alembic не изменилась: проверка «модели = миграции» проходит без новой миграции.

Снимок делается из прежних классов — после переключения его не пересоздавать (прежних
классов больше нет): он фиксирует то, что было.

## 4. Углы

* **Порядок.** Порядок столбцов в таблице БД, полей DTO и записей настроек у прежних
  таблиц разный — для них заданы `column_order`, `dto_order`, `config_order`. У новых
  таблиц достаточно порядка полей описания.
* **Комментарий таблицы и `sqlite_autoincrement`** — в `__table_args__` (без них
  autogenerate увидел бы различие с базой).
* **Ссылки DTO по имени** (`photos: List['PhotoDTO']`) — разрешаются `rebuild_dtos` после
  создания всех DTO.
* **Настройки — копия на каждую сборку** (`_copy_config`): правка словаря одного экрана не
  задевает другой. Функции (`compute`, `formatter`) не копируются — общие.
* **`__module__`** сгенерированных классов — модуль, где они объявлены (`module=__name__`):
  иначе классы «жили» бы в `app.schema.define` (логи, сериализация, сообщения ошибок).
* **Связь заметки** `<x>_note` — без `back_populates`, как было; у `AppointmentNote.appointments`
  `back_populates='note'` — как было.
* **`has_photos`** (подзапрос в запросе приёмов) нужен старым экранам; набору — `photo_count`
  (`skip=('has_photos',)`).
* Описание не должно импортировать модели, DTO или сервисы — модуль моделей импортирует его.
