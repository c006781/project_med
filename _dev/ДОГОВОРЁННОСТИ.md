## Как коммитить

Режим «Как коммитить» (25.10.2026) — так коммиты делались в этом проекте; отличается от
skill п. 4 (там — поимённо и коммит путями).

1. **Ветка.** Правка — в ветке темы: подходящая по смыслу уже есть — `git checkout -q
   rework_work/<тема>` и `git merge -q rework`; нет — `git checkout -q -b rework_work/<тема>`
   от `rework` (только `rework`, `rework_work/*`, режим «Ветки»).
2. **Что изменено.** `git status --short` перед добавлением. Неотслеживаемые и изменённые
   файлы не мои (файлы пользователя в корне, бэкапы, копии конфигов) — не добавлять.
   В индексе ничего чужого: `git diff --cached --name-only` пуст до моего `git add`.
3. **Добавление — папками правки:** `git add <папка> <папка> <файл>` (например,
   `git add app tests _dev`) или `git add -A <папка>` (вместе с удалёнными и новыми
   файлами в ней). Нельзя: `git add -A` / `git add .` для всего корня, `git commit -a`.
   Если в добавляемой папке есть изменённые пользователем файлы — эту папку добавлять
   поимённо, без них, и сказать о них в ответе.
4. **Секреты и данные** не попадают: их закрывает `.gitignore` (`*.env`, `*.db`,
   `*.msgpack`, `photos*/`, `.coverage`); в выводе `git status --short` их быть не должно —
   есть → не коммитить, сказать.
5. **Коммит:** `git commit -q -m "<заголовок>" -m "<тело>"` (сообщение — как в skill п. 4)
   — весь индекс (в нём только моё, п. 2–3).
   Хуки не обходить (`--no-verify` нельзя); упал хук — сообщить.
6. **Проверка:** `git show --stat HEAD` — состав коммита совпал с задуманным (только мои
   файлы); `git -c core.quotepath=off status --short` — осталось только чужое
   (неотслеживаемое не моё). `core.quotepath=off` — иначе русские имена выводятся кодами.
7. **Когда:** после каждого законченного шага (подзадачи) с проверкой — тесты без новых
   падений относительно эталона; при проходах ревью — коммит на каждый проход.
8. **Слияние** (режим «Ветки»): тема закончена — `git checkout -q rework` →
   `git merge -q --no-ff rework_work/<тема> -m "Слияние rework_work/<тема>: <кратко>"`; конфликт —
   не решать наугад: показать и спросить. Ветку темы не удалять. Push — никогда сам.

## Правила кода проекта

Указания владельца 14.10.2026 (в памяти — с того же дня); дополняют skill п. 7–8.

* **Документирование всего, что пишу и правлю:** модуль, класс, функция, метод — подробный
  докстринг с примером, полная типизация параметров и возврата. Формат докстринга — как в
  skill п. 7 и его образце `docstring_example.py` (Google: `Args:`, `Returns:`, `Raises:`,
  `Example:` с `>>>`) — с 30.10.2026 (было «Пример:», 14.10.2026). Старые «Пример:»,
  «Аргументы:», `:param` — переводить по мере правок (в правимой функции), массово не
  переводить (решение владельца 30.10.2026).
* **`IMPLEMENTATION.md` у каждого модуля / пакета:** что делает, проблемы, углы, решения,
  журнал (дата — что — зачем).
* **Комментарии и закомментированный код проекта — намеренные** (объясняют, почему сделано
  так): не удалять пачкой, не «чистить». Заменяя код проекта, старую версию оставлять
  закомментированной с пометкой `# ↑ до <ГГГГ-ММ-ДД> (<номер находки>): <причина>` (или
  `↓` над блоком). Свой код, написанный в той же работе (до коммита), — можно менять свободно.
  Копию старой версии — **только при изменении логики**; чисто форматные правки (параметр
  на строку, типы, докстринги) — без копии, откат — по git (решение владельца 26.10.2026,
  `_dev/ВОПРОСЫ.md` В-6).
* **Самопроверка проходами:** проход → исправление → запись (`IMPLEMENTATION.md`,
  `ПРОГРЕСС.md`) → тесты → коммит; повторять, пока проход не будет чистым (skill п. 8).
* Тесты и проверочные запуски — на временных `.env`, `config.msgpack`, базах (см.
