## 1. Зачем миграции

До 2026-10-16 база создавалась `Base.metadata.create_all`. Он только СОЗДАЁТ недостающие
таблицы: новый столбец, индекс или изменение типа в существующей базе не применяется. Базы,
созданные в разное время, расходились со схемой — у настоящей базы проекта не было индекса
`ix_appointment_note_text`, который есть в модели.

## 2. Как работает (`upgrade_database`, вызывается из `Database.__init__`)

| База | Что происходит |
|---|---|
| новая (пустая) | все миграции с первой |
| с отметкой версии (`alembic_version`) | недостающие миграции; перед ними — резервная копия файла |
| старая без отметки (create_all) | приведение к исходной схеме `0001_baseline` (см. §3) → отметка → дальнейшие миграции |
| последняя версия | ничего (файл не трогается) |

* **Резервная копия** перед любым изменением существующей базы-файла:
  `<файл>.bak-<ГГГГММДД_ЧЧММСС>-<версия>` (для старой базы — `-legacy`).
* **Транзакции (MG1).** Драйвер SQLite (pysqlite) фиксирует CREATE/ALTER/DROP сам, мимо
  транзакции — сбой посреди миграции оставил бы базу полуобновлённой. Миграции идут через
  отдельный движок с настоящими транзакциями (рецепт SQLAlchemy: драйвер не управляет
  транзакциями, `BEGIN` — явно): сбой — откат ВСЕГО, включая DDL. Основной движок
  приложения не меняется.
* `render_as_batch=True` — SQLite почти не умеет ALTER TABLE, Alembic пересобирает таблицу.
* `create_tables(recreate=True)` удаляет и `alembic_version` — иначе пустая база считалась бы
  свежей.

## 3. Старые базы без отметки версии

Сравнение — со схемой, которую строит САМА исходная миграция (во временной базе в памяти),
а не с текущими моделями (они меняются).

| Отличие | Что делаем |
|---|---|
| нет таблицы / индекса / необязательного столбца | **дописываем** (create_all этого не делал — базы разных лет отличаются) |
| лишнее: старые столбцы (`email`), посторонние таблицы, другие индексы, иные типы | **не трогаем** — данные не теряются; предупреждение в журнал |
| нет обязательного столбца без значения по умолчанию | **отказ** (`MigrationError`), база не меняется |

Ограничение: дописанный недостающий столбец — без внешнего ключа (SQLite не умеет
добавить связь к существующей таблице без пересборки; Alembic упал бы). Данные это не
затрагивает; связь появится, если позже миграция пересоберёт таблицу.

## 4. Как добавить изменение схемы

1. Изменить модель в `database_shema/clinic.py`.
2. Создать миграцию (из корня проекта; консоль работает с ОТДЕЛЬНОЙ базой разработчика
   `migrations_dev.db`, не с настоящей — MG11):
   `alembic -c app/database/migrations/alembic.ini upgrade head` — довести её до текущей версии;
   `alembic -c app/database/migrations/alembic.ini revision --autogenerate -m "что меняем"`.
3. Вычитать файл в `migrations/versions/`, дописать «что меняет и почему».
4. Тест `test_models_match_migrations` упадёт, если модель изменили, а миграцию нет.
5. Настоящая база обновится сама при запуске программы (копия, блокировка, проверки).

**Правила для миграций** (они же — в шаблоне `script.py.mako`):

* Модели приложения в миграциях НЕ импортировать: модели меняются, миграция — нет. Для
  данных — `op.execute(...)` или `sa.table('patients', sa.column('phone'))`.
* Применённую (выпущенную) миграцию не менять и не удалять — только новая поверх.
* `downgrade` — обратное действие; если обратного нет (удалённые данные) — явный
  `raise` с объяснением, а не тихая заглушка.
* Изменение столбца/ограничения в SQLite — через `op.batch_alter_table` (autogenerate
  делает так сам: `render_as_batch`). Таблица пересобирается; внешние ключи на это время
  выключены (MG10), после миграции проверяется, что новых «висячих» ссылок нет.
* Данные + схема — в одной миграции можно: всё в одной транзакции, сбой — откат всего.
* **Пересборка таблицы удаляет её триггеры** (Р-10): `batch_alter_table` с пересборкой — внутри
  `with sqlite_triggers.keep_triggers():` (§12). Команды данных вне блока вызывают триггеры.
* **Имена связей.** У моделей — правило именования `NAMING_CONVENTION` (`clinic.py`, A2):
  новые внешние ключи получают имя `fk_<таблица>_<столбец>_<куда>`. У ключей в базах,
  созданных до 2026-10-18, имён нет. Удалить/изменить такую связь —
  `op.batch_alter_table('photos', naming_convention=NAMING_CONVENTION)` и дальше по имени
  из правила (проверено тестом на старой базе). Из приложения в миграции можно брать
  только `NAMING_CONVENTION` (постоянна; правило «модели не импортировать» — про классы).
* Две ветки разработки добавили миграции от одной версии — две «головы»: программа
  откажется запускаться, нужна миграция-слияние (`alembic merge heads`).

Имена файлов миграций — латиницей (`0001_baseline.py` …).

**Запуск разных версий программы на одной базе.** Новая база + старая программа
(версия базы ей неизвестна) — отказ с понятным сообщением, база не трогается (MG9).

  2026-10-30, ТД-9). `Database.Session` — `scoped_session`: одна сессия на поток, `close()`
  её не заменяет, списки живут дольше транзакции. Поэтому обработчик `after_commit`
  выполняет «после коммита» и **отбрасывает** «при откате», `after_rollback` — наоборот;
  иначе чужую запись выполнила бы следующая транзакция потока (удалялся сохранённый файл
  фото). Неудавшееся удаление (файл занят) помечается `retry` и не отбрасывается — его
  повторит следующее событие того же вида. `rollback()` без начатой транзакции (в блоке не
  было запросов) SQLAlchemy событий не шлёт — `session_scope` перед откатом начинает пустую
  транзакцию (соединение не открывается). Сессия, полученная `get_session()` и откаченная
  без транзакции вручную, этой защиты не получает. FD10 (2026-10-31): удаление «после
  коммита», запланированное при неактивной сессии (flush упал, коммита не будет), файл не
  трогает — предупреждение в журнал (`app/utils/IMPLEMENTATION.md`, FD10); раньше
  `schedule_deletion` удалял сразу.

## 9. Исключения базы и значения запросов в журнале (2026-10-31, М8, Ф1.6.7в)

| Где | Ошибка драйвера | Что выбрасывается |
|---|---|---|
| `Database.__init__` (открытие и `upgrade_database`) | `sqlalchemy.exc.DatabaseError`, `sqlite3.Error` (резервная копия — backup-API мимо SQLAlchemy) | `DatabaseConnectionError(database_error_text(exc), details={база, операция}) from exc`; движок освобождается. `MigrationError` — как раньше |
| `session_scope` (блок и коммит) | `sqlalchemy.exc.IntegrityError` | `DbIntegrityError(что нарушено, details={таблица, операция, SQL}, original=exc.orig) from exc` — после отката; остальные — как есть |

* **Текст пользователю.** «Занята другой копией» / «нет доступа» / общий — одна функция
  `migrate.database_error_text` для `Database.__init__` и `startup_error_text` (раньше разбор
  жил только в окне запуска). `startup_error_text` на `DatabaseConnectionError` отдаёт её
  `detail` (без кода `[6002]`). Нарушение целостности — по сообщению SQLite
  (`_integrity_detail`: повтор уникального, пустое обязательное, внешний ключ, CHECK; поле —
  если SQLite его назвал); таблица и операция — из текста SQL (`_statement_target`).
* **Журнал** пишет `session_scope` — `log_text()` (подробности, исходная ошибка) с
  трассировкой; у исключения приложения из блока — тоже `log_text()`, у прочих — прежнее
  `Ошибка: <текст>`. Журнал пишется до `raise … from`, поэтому `original` у
  `DbIntegrityError` задаётся явно (`exc.orig`): цепочки в этот момент ещё нет (найдено
  тестом). Окно запуска (`interfaces/gui/gui_window/main.py`) пишет `log_text()` ошибки
  открытия.
* **Значения запросов** (ФИО, телефоны, тексты — личные данные) SQLAlchemy кладёт в текст
  своих ошибок (`[parameters: …]`), а с ним — в трассировку цепочки: убрать их только из
  `details` было бы мало. Поэтому движок создаётся с `hide_parameters=True`; для отладки —
  настройка `LOG_SQL_PARAMS` (`Database(log_sql_params=True)`, решение владельца
  2026-10-31): значения видны в ошибках и в `details['параметры']`, при открытии базы —
  предупреждение в журнал. Флаг задаётся движку при создании — его смена переоткрывает
  базу (`ConfigApplier.apply_database`, блок `database`); переключатель на экране — Ф2.2.7.
* Внешние ключи в основном движке включены с 2026-11-01 (Р-2, Ф1.6.7г шаг 5:
  `PRAGMA foreign_keys=ON` на каждом соединении, `Database(foreign_keys=False)` — как раньше;
  движок миграций их по-прежнему выключает сам, MG10): висячая ссылка и удаление строки, на
  которую ссылаются, — `DbIntegrityError` «нет связанной записи или на запись ссылаются
  другие». До включения данные рабочей базы проверены: `PRAGMA foreign_key_check` пуст.
* Тесты: `tests/test_database_shema/test_database_errors.py` (на коде до правки 22 из 24
  падают), `tests/test_config/test_manager_behavior.py` (флаг: `apply_database`, `get_db`).

## 10. События таблиц (2026-11-01, Ф1.6.7г; решение владельца 2026-10-31, В-19)

Как события объектов в RAD Studio: у таблицы места «перед / после добавления, изменения,
удаления строки», «перед коммитом», «после коммита / отката»; к ним по имени подключаются
действия в описании таблицы (`TableDef(events=(on('after_delete', 'имя'),))`,
`app/schema/define.py`). Исполняет — `table_events.py`.

| Часть | Как |
|---|---|
| Реестр | `register_action(имя)` — функция `action(ctx: EventContext)`. Описание модули не импортирует (К6). Действия верхних слоёв регистрирует сборка приложения ДО открытия базы |
| Проверка имён (Р-9) | `Database.__init__` → `check_action_names(Base)` до создания движка: неизвестные имена — `TableEventError` со списком «таблица.место: имя», база не открывается |
| События строк | Общие для процесса обработчики на класс `Mapper` (ставятся один раз); диспетчер — из `session.info['table_events']`. Сессия не из `Database` (нет диспетчера) — ничего. Срабатывают внутри flush, в том числе при каскаде и «сиротах» (проверено синтетикой и тестом) |
| Диспетчер (Р-8) | `TableEvents` — свой у каждого `Database`: `sessionmaker(info={...})` + `listen(фабрика)` (повтор для той же фабрики — без второй регистрации). `reopen_db` — новый `Database`, новая фабрика, повторов нет (тест) |
| Прежние значения | `before_update`: из истории атрибута, а если её нет (меняли, не загрузив) — строка из базы по первичному ключу через соединение flush; `before_delete` — строка из базы (для журнала). История ORM к коммиту уже очищена — поэтому снимается при сбросе, не в `before_commit` (Р-3) |
| Журнал транзакции | Только таблицы с действиями транзакции: `RowChange(таблица, операция, ключ, значения, прежние)`; в `session.info`, привязан к корневой транзакции (слабая ссылка), забирается при коммите, при откате и в `after_transaction_end` транзакции, закрытой без них (`close()` / `remove()` — как откат: действия «после отката», предупреждение; Р-16). Журнал чужой транзакции в `session.info` отбрасывается с предупреждением (сессия живёт дольше транзакции — как ТД-9) |
| Точки сохранения (Р-18) | `before_commit` / `after_commit` / `after_rollback` SQLAlchemy шлёт и для `begin_nested` — там пропускаются (`in_nested_transaction()`): «после коммита» не выполнится до коммита внешней транзакции. Строки отката точки сохранения остаются в журнале — ORM-точек сохранения в программе нет. Обработчики ТД-9 (`database.py`) так же уязвимы — не трогались, записано в РИСКИ |
| «Перед коммитом» | `flush` (журнал полон) → действия таблиц с изменёнными строками — один раз (не в цикле: в общем цикле со сборщиком пара действий зацикливается — разбор предела, О4); могут менять данные. Сборщик мусора — последним (шаг 3) |
| Действие строки меняет сессию (Р-21) | Добавило / удалило строки сессии внутри flush (число `new` / `deleted` изменилось за вызов) — `TableEventError`: SQLAlchemy такие правки молча теряет или вставляет после уборки |
| Ошибки (Р-12, Р-5) | Исключение приложения из действия — как есть (намеренный отказ), другое — `TableEventError` (6003; `details`: таблица, место, действие, id; цепочка `from`); `session_scope` откатывает. После коммита / отката — только журнал, остальные действия выполняются |

### 10.1 Сборщик мусора (шаг 3; предел — решение владельца 2026-11-01 по разбору)

Таблица `TableDef(keep=KEEP_USED)` — «только используемые»: строку, на которую в транзакции
убрали последнюю ссылку, удаляет сборщик перед коммитом, в той же транзакции.

| Часть | Как |
|---|---|
| План (при открытии) | `TableEvents.configure(Base)` → `_CollectorPlan`: таблицы «только используемые», граф освобождения (U → V, если строка U или строка, удаляемая ORM вместе с ней каскадом, ссылается на V), **глубина** — число таблиц на самом длинном пути, **предел рабочих кругов = глубина + 1**. У заметок глубина 1, предел 2. Круг в графе (самоссылка, A ↔ B) — `TableEventError` при открытии (подсчёт ссылок такие строки не соберёт, число кругов зависело бы от данных; Р-20). Составной ключ таблицы «только используемые» — ошибка |
| Кандидаты (Р-3) | В событиях строк при сбросе, после действий места: `before_update` — прежнее значение изменённой ссылки (история или строка из базы), `before_delete` — все ссылки строки (строка из базы; каскад и «сироты» — свои события). Ссылки смотрятся у любой модели, в том числе без описания. Удалённые строки «только используемых» в транзакции — отметка «удалено» (новая строка с тем же id её снимает, Р-19) |
| Порядок перед коммитом | сброс → действия «перед коммитом» **один раз** → сборщик → журнал закрыт. Кандидаты после закрытия (чужие слушатели `before_commit`, их правки SQLAlchemy досбрасывает сам — `before_commit` повторно не вызывается) не проверяются: предупреждение после коммита, следующей транзакции не достаются (Р-15) |
| Круг | сброс → кандидаты, кроме удалённых → проверка одним запросом на таблицу (строка есть и `NOT EXISTS` по всем внешним ключам на таблицу из метаданных, только таблицы, существующие в базе; порции по 500 id) → удаление через ORM в `no_autoflush` с `expire` обратных коллекций (Р-17). Рабочий круг — есть кандидаты или сессия снова изменена после сброса; иначе — неподвижная точка |
| Предел | Круг сверх глубины — предупреждение (схема учтена не полностью, сохранение проходит); сверх предела — `TableEventError` «уборка ненужных записей не закончилась — сработала защита от зацикливания; изменения не сохранены», откат всей транзакции; повторный коммит без отката — снова ошибка. Время, число удалений, повтор кандидатов не ограничиваются (законно растут) — в `details`: круги, кандидаты последнего |
| Почему так (разбор) | Сам сборщик завершается без предела (каждый круг только удаляет); зациклить может только чужое изменение данных во время уборки — поэтому действия «перед коммитом» не в общем цикле (в общем цикле пара «создать пустую заметку ↔ отвязать пустую» шла без конца). Постоянный предел «10» для заметок в 10 раз шире нужного и отказывал бы на законной цепочке длиннее 10. Превысить точную границу можно только ошибкой — коммит сохранил бы её результат, поэтому откат |
| Журнал (Р-11) | После коммита — по строке на удаление: таблица, id, какое изменение убрало последнюю ссылку (таблица, id, столбец), круг; без текстов (личные данные). После отката — ничего |
| Полная проверка (кнопка, М19) | `find_unused(session)` — все строки без ссылок (только чтение, список «будет удалено»); `delete_unused(session, список)` — удаляет только те, что и сейчас без ссылок; освобождённые ими — обычная уборка при коммите |

Ограничения: действия строк — внутри flush, менять сессию в них нельзя (SQLAlchemy), только
читать через `ctx.connection`; изменения мимо ORM событий не вызывают — в коде программы их
нет, тест `test_orm_only.py` (Р-1; миграции — исключение).

## 12. Встроенные триггеры SQLite (2026-11-07, Ф1.6.7д; решение владельца 2026-10-31, В-19)

Для правил только внутри данных: срабатывают и через ORM, и при сыром SQL, и при правке
сторонней программой; вне базы ничего не умеют (файлы, журнал программы — события таблиц, §10).
Сейчас — только поддержка в описании и миграциях: в описаниях клиники триггеров нет, новой
ревизии нет (номер 0003 не занят).

| Часть | Как |
|---|---|
| Описание | `TableDef(triggers=(trigger('имя', 'before_delete', 'команды', when=…, of=…),))`, `app/schema/define.py`; места — те же имена, что у строк событий. Форма (имя, место, пусто, `of` только у изменения, столбец `of` есть, повтор на таблице) — `ValueError` при описании |
| Путь текста | `build_model` → `Table.info[TRIGGERS_INFO]` (имя → `CREATE TRIGGER`); `to_metadata` копирует. `schema_at` дописывает туда текст из базы (`attach_stored_triggers`, `reflect` их не читает) — поэтому модели и схема последней миграции сравниваются с базой одним кодом |
| Опечатка (по образцу Р-9) | SQLite принимает `CREATE TRIGGER` с несуществующей таблицей или столбцом и падает при срабатывании. `check_trigger_definitions` в `Database.__init__` (до движка), в `generate_migration` и проверке сборки: временная база в памяти, каждый триггер создаётся, его операция компилируется (`EXPLAIN`), повтор имени на разных таблицах (имена едины на базу) — `MigrationError`, все ошибки списком, файл базы не создаётся. Нет триггеров — базы в памяти нет, стоимость нулевая |
| Сравнение | Alembic триггеры не видит, поэтому `_compare_triggers` подключён к его autogenerate (`comparators.dispatch_for('schema', priority=LAST)`: после таблиц, иначе в файле триггер шёл бы раньше своей новой таблицы). Отличия — `add_trigger`, `remove_trigger`, `modify_trigger` в `compare_metadata`, а значит в `schema_differences`, `pending_model_changes`, `_plan_repair`, `describe_differences`. Текст сравнивается после `normalize_sql` (пробелы и переводы строк вне строковых значений). Посторонняя таблица и её триггеры не рассматриваются |
| Подключение | При импорте `sqlite_triggers`: его импортируют `migrate.py` и `migrations/env.py` (консольный `alembic` идёт мимо `migrate`) |
| Генератор | Все три отличия безопасны (`is_safe_addition`): данные не меняются, в файле оба текста, `downgrade` возвращает прежний. Запись в файл — `TriggerChangeOp`: `DROP TRIGGER IF EXISTS` + `CREATE` через `exec_driver_sql` (`op.execute` прочёл бы `:x` в тексте как параметр запроса) |
| Новая база | Триггер создаёт миграция, как всё остальное |
| Старая база без отметки | Исходная схема без триггеров: приведение, отметка, затем миграции создают их. Триггер сторонней программы — «лишний» |
| Автодостройка (версия последняя) | Образец — схема последней миграции. Нет в базе — дописать; другой текст — заменить текстом миграции, предупреждение в журнал (данные не меняются, а правило программы на месте; решение исполнителя, вынесено владельцу); лишний — оставить, запись DEBUG. Быстрый путь `upgrade_database` видит это тем же `_drift_plan`: нечего чинить — файл не трогается. Каждый пункт в своей точке отката (A5): сбой между снятием и созданием возвращает прежний текст |
| Р-10, пересборка | `batch_alter_table` с пересборкой: новая → перенос → удаление старой → переименование. Удаление забирает триггеры таблицы молча. Триггер ДРУГОЙ таблицы, упоминающий пересобираемую, роняет переименование («error in trigger …: no such table», SQLite 3.25+), транзакция откатывается. `keep_triggers()`: снимает ВСЕ триггеры базы, после блока создаёт с прежним текстом (кроме триггеров удалённых таблиц и созданных в блоке заново). Текст — из самой базы: миграция не зависит от описания |
| Забыли `keep_triggers` | Не молча: 1) в памяти голова без триггера → `pending_model_changes` и тест «модели = миграции» показывают `add_trigger`, сборка останавливается; 2) автомиграция с пересборкой (новая связь — `add_fk`) проверяется применением в памяти (`_refuse_lost_triggers`): потеряла или упала — файл удаляется, `MigrationError` «напишите вручную с keep_triggers» |
| MG14 | **После миграции** `_check_triggers`: все триггеры базы компилируются; новая ошибка — откат всей транзакции (столбец, нужный триггеру, удалён: иначе запись падала бы уже у пользователя). Ошибки, бывшие до миграции (чужой триггер), не мешают — как старые висячие ссылки, MG10 |
| Откат | Триггеры — обычные строки `sqlite_master`: транзакция движка миграций (MG1) откатывает их, в том числе снятые `keep_triggers`. Частичных триггеров нет (тесты) |
| Резервная копия | backup-API копирует и триггеры (тест) |

### Подводные камни

* **ORM не знает, что триггер изменил данные (Р-10).** Загруженные объекты устаревают до
  `session.refresh` / `expire` или конца транзакции (тест; докстринг `trigger`). События таблиц и
  сборщик мусора таких изменений не видят (Р-1): ссылку, снятую триггером, сборщик не заметит —
  найдёт полная проверка `find_unused`. Поэтому ссылки на «только используемые» таблицы
  триггерами не менять.
* **Внешние ключи (Р-2).** В основном движке действуют и на команды триггера (висячая ссылка —
  `DbIntegrityError`, откат всей транзакции; тест). В движке миграций выключены (MG10).
* **Запрет** — `RAISE(ABORT, 'текст')`: `DbIntegrityError` с этим текстом (тест). `RAISE(IGNORE)`
  с ORM нельзя: ожидается изменённая строка, `StaleDataError` (тест). `BEFORE`-триггер не должен
  менять саму строку (в SQLite поведение не определено).
* **`lower` / `upper`** в программе свои (понимают кириллицу, APP1), в миграции и у сторонней
  программы — встроенные. Правило на них работало бы по-разному.
* **Команды данных в миграции** вызывают триггеры (внутри `keep_triggers` — нет).
* **`EXPLAIN` и кеш `sqlite3`.** Модуль кеширует подготовленные запросы по тексту, а `EXPLAIN`
  версию схемы не сверяет: повтор того же текста после DDL показал бы старый план без ошибки
  (проверено на 3.34.1). Поэтому в конце запроса — уникальный номер (`_explain_counter`). Для
  `UPDATE` названы все столбцы — иначе `UPDATE OF` не компилировался бы.
* **Текст после переименования.** `ALTER TABLE … RENAME` переписывает в триггерах упоминания
  таблицы, и версии SQLite (3.34 и 3.37 на двух машинах) могут записать это по-разному: автодостройка
  разово заменит текст; данных это не касается.
* **Триггер сторонней программы** при пересборке вне `keep_triggers` пропадает или роняет
  миграцию — как любой чужой объект. `0002_photo_files` применённая, её не меняем.
* **`tests/test_database_shema/test_orm_only.py`** ищет строки, начинающиеся с `UPDATE … SET` и т. п.:
  первое настоящее правило в `app/schema/clinic.py` с таким текстом попадёт под его образец — текст
  начать с новой строки (проверка построчная) или решить вместе с первым правилом.

Тесты — `tests/test_database_shema/test_sqlite_triggers.py`, `tests/test_schema/test_trigger_def.py`.

## 8. Автомиграции (2026-10-18)

Три части; опасные изменения (переименование, смена типа, перенос данных) — всегда вручную:
автоматика видит переименование как «удалить + добавить» и потеряла бы данные.

| Часть | Где | Что делает |
|---|---|---|
| **Применение** | каждый запуск (`Database.__init__` → `upgrade_database`) | недостающие миграции, копия, блокировка, откат при сбое (§2) |
| **Автодостройка** | каждый запуск, после миграций (`MigrationSettings.repair_drift`, по умолчанию да) | база сравнивается со схемой ПОСЛЕДНЕЙ миграции (`schema_at(head)`, собирается в памяти один раз за процесс): недостающее безопасное — таблица, необязательный столбец, индекс — дописывается (копия `…-<версия>-repair`); лишнее не трогается (запись в журнал уровня DEBUG — иначе повторялась бы при каждом запуске); нет обязательного столбца — отказ. Тот же механизм, что для старых баз (§3), только образец — последняя схема |
| **Генерация миграции** | запуск из исходников (`main_gui_window.py` → `configure(autogenerate=True)`), сборка | модели сравниваются со схемой последней миграции в памяти (`pending_model_changes`); только безопасные добавления → файл `versions/<NNNN>_auto_<дата_время>.py` с описанием (`generate_migration`), затем он применяется как обычная миграция; небезопасные — отказ «напишите миграцию вручную» (окно запуска покажет) |
| **Проверка сборки** | `scripts/build_win.py` перед PyInstaller | `python -m app.database.migrate check --generate`: одна «голова», модели = миграции; безопасные отличия → файл миграции и ОСТАНОВКА сборки (просмотреть, добавить в git, собрать снова); код 0 — всё в порядке |

* **В exe генерации нет**: файлы миграций там во временной папке (`_MEI…`) и пропали бы;
  совпадение моделей и миграций гарантирует проверка при сборке.
* **В тестах генерации нет** (по умолчанию выключена): тесты регистрируют свои модели на общей
  `Base` — иначе тест создал бы файл миграции в настоящей папке `versions`. Тесты подменяют
  модели через `migrate._default_metadata`.
* **Номер автомиграции** с датой и временем — две ветки разработки не получат одинаковый;
  если обе добавили миграции — две «головы», запуск и сборка остановятся (нужен `alembic merge heads`).
* **Стоимость** автодостройки при запуске — ~16 мс на базе проекта (без неё ~1 мс): сборка
  схемы в памяти один раз и сравнение. Растёт с числом таблиц и миграций; отключается
  `configure(repair_drift=False)`.
* Автомиграция, созданная при запуске из исходников, — обычный файл: его нужно просмотреть
  и добавить в git (в журнал пишется предупреждение с путём).
* **Что считается безопасным** (`is_safe_addition`, `unsafe_changes`): новая таблица (с её
  индексами и связями); необязательный столбец или столбец со значением по умолчанию;
  обычный индекс; связь, все столбцы которой новые. **Небезопасно:** удаление, смена типа
  или обязательности, связь на существующий столбец, уникальный индекс на существующей
  таблице (A4: повторы в данных клиники уронили бы миграцию).

* Удалили файл автомиграции, уже применённой к базе разработчика, — база «новее программы»
  (MG9): вернуть базу из резервной копии `.bak-…` рядом с ней.

  автомиграции — две «головы»; следующий запуск остановится с понятным сообщением.
