## 1. Зачем

Проверка 2026-10-18: вывести новую таблицу на экран через наборы данных — 7 строк, но
подключить её «целиком» (черновики, пилотный экран) требовало правок в 4 местах: схема и
адаптер черновиков (`app/draft/integration.py`), перечень наборов и связей
(`app/dataset_app/factory.py`), словари колонок и форм экрана, поставщик сервиса. Опыт с
черновиками падал: `SchemaError: неизвестный тип сущности 'prescription'`.

Теперь из одного описания:

| Что | Откуда |
|---|---|
| поля набора | `field_configs` + DTO + модель |
| свои столбцы | `extras`: `mark` (отметка), `calc` (по строке), `total` (итог по подчинённым) |
| родитель и поле связи | внешний ключ модели на таблицу реестра (неоднозначно — `parent`) |
| схема черновиков | `drafts_schema()` — совпадает с прежней ручной (тест) |
| запись черновиков | `service_adapter()` |
| наборы, источники, связи | `build()` |
| колонки и форма экрана | `columns`, `form` |

## 2. Вычисляемые столбцы (решения владельца 2026-10-18)

| Вид | В описании | Считает | Черновики | Сортировка |
|---|---|---|---|---|
| отметка (галочка) | `mark()` | — (своё поле набора) | — | когда загружено всё |
| по строке | `calc(имя, подпись, функция)` (функция от строки или от строки и сервиса) | программа | видит | когда загружено всё |
| итог по подчинённым | `total(имя, подпись, таблица, func, field, where)` | программа, пачкой на окно | видит | когда загружено всё |
| итог по подчинённым | поле `field_configs` с `sql_compute` (как `has_photos`) | база | не видит до сохранения | по всей таблице |

Итог по подчинённым — способ на выбор в описании столбца. «Чеки»: отметки строк — `mark()`;
итоги по таблице чеков — `total(...)` у пациента/приёма, когда таблица чеков появится
(одним описанием).

## 2.1. Связи (2026-10-18)

| Вид | Откуда | Удаление | Экран |
|---|---|---|---|
| владение (родитель) | внешний ключ на таблицу реестра (неоднозначно — `parent`) | каскад с подтверждением; дети удаляемой — «удаляется с родителем», правка разрешена | главная → подчинённая |
| ссылка | остальные внешние ключи на таблицы реестра; настройка — `links=(ref(поле, таблица, on_delete, collect, display),)` | по правилу: запрет (по умолчанию) / обнуление / каскад; `collect` — переиспользуемые данные удаляются, когда никому не нужны | показ текста цели вместо id; выбор из списка (записи БД + новые несохранённые) |

## 2.2. Итоги, которые считает БД — отдельным объектом (2026-10-18)

Мысль владельца: считать итог (число фото у приёма) в БД, но НЕ в запросе самой таблицы
данных (подзапрос `sql_compute`, как старый `has_photos`, утяжеляет этот запрос и мешает
вносить и править данные). Отдельный объект (`SqlTotals`, ядро — `KeyedTotals`) делает свой
`SELECT связь, COUNT(*)… FROM подчинённая WHERE связь IN (:ключи окна) GROUP BY связь` и
связывается со строками по ключу; все `total(by='sql')` таблицы по одной подчинённой — одним
запросом на окно; ключи — кусками по 500.

* Черновики — поправка `unsaved='delta'` (по умолчанию для чисел строк): + новые
  несохранённые подчинённые, − помеченные на удаление и перенесённые (способ записи
  сообщает `pending`); `'ignore'` — только БД.
* Запрос таблицы данных — без подзапросов итогов: сервис получил необязательный параметр
  `sql_compute` (какие такие поля считать; `None` — все, как раньше), набор просит только
  описанные; `skip=('has_photos',)` убирает старый итог из набора приёмов (старые экраны
  показывают его по-прежнему).
* В клинике: «Фото» у приёма и «Приёмов» у пациента — `by='sql'`.
* Сортировка по таким столбцам — как у остальных, которые считает не источник: когда
  загружено всё (по всей таблице — потребовался бы JOIN в запросе данных, чего и избегаем).

## 2.3. Общие данные — заметки (2026-10-31, ПЛАН Ф1.3.4)

Заметки (`appointments_notes`) — общий текст: одну заметку используют многие записи (поля
`*_id` пациента и приёма; сервис находит заметку по тексту и переиспользует). Раньше
черновики о заметках не знали: ключи на заметки отбрасывались (`references_of`), в реестре
заметок не было.

Решение: **заметки — в реестре `CLINIC` как общие данные** (`TableSpec.shared=True`,
`table_spec(NOTES, shared=True)` в `clinic.py`); описание `NOTES` в `app/schema` и
`CLINIC_DEFS` (наборы экранов) не менялись.

| Что | Общие данные (`shared`) |
|---|---|
| дерево (`names`, `chain`, `children`) | не участвуют: ни родителем, ни подчинённой (`SpecError`, если указать) |
| наборы (`build`) | не собираются (экрана заметок пока нет) — `shared_names()` |
| ссылки | все внешние ключи на них (`foreign_keys_of`, в т. ч. на заметки) — `Link`, по умолчанию `restrict`, `collect=False` |
| черновики | корневой тип после дерева (`drafts_schema`); адаптер — с их сервисом (`service_adapter`) |

Почему так, а не `NOTES` в `CLINIC_DEFS`:
* `CLINIC_DEFS` — реестр наборов экранов: строка там дала бы набор заметок на каждом
  экране (лишний запрос при открытии), а дерево и тесты, считающие таблицы, поменялись бы;
* ключи на заметки отбрасываются `references_of` нарочно (заметка — не родитель записи), так
  что «просто добавить строку» всё равно потребовало бы признака «только ссылки»;
* правка остаётся в `app/tables` (+ `foreign_keys_of`), `app/schema` не меняется.

Почему `collect=False` («удалять, когда ни на что не завязана» — не в черновиках): ставшие
ненужными заметки уже удаляет сервис записи (`NoteService.cleanup_unused_note` — при
удалении записи и при смене текста, по схеме БД, DYN2). `collect` в черновиках удалял бы ту же
заметку второй раз (сервис уже удалил → «не найдено» → откат) и не видел бы смену текста.
Черновики отвечают за запрет: удалить заметку, на которую ссылаются записи БД или
несохранённые черновики, нельзя — понятный отказ «Нельзя удалить «Заметка #5»: на неё
ссылаются записи: «Пациент #1»» и откат всего сохранения.

Углы:
* В строках наборов `*_id` заметок нет: DTO исключает их из `model_dump` — показ текста
  ссылки и список выбора у этих полей (как у любой ссылки) пока не используются (поля
  скрыты); текст заметки — поле записи `*_text`.
* Заметку освободила правка записи в том же сохранении (сменили текст), а её саму пометили
  на удаление: сервис удаляет её при правке, исполнитель черновиков — пропускает уже
  удалённую цель ссылок (`app/utils/drafts` executor, 2026-10-31), а не падает «не найдено».
* Правка текста заметки как записи (будущий редактор заметок) изменит текст у всех, кто на
  неё ссылается, — это решение для экрана (ВОПРОСЫ, М15).

## 3. Подключено

* `app/draft/integration.py`: `build_app_schema` и адаптер в `create_app_drafts` — из
  `CLINIC` (прежний код — комментарием).
* `app/dataset_app/factory.py`: `create_clinic_datasets` → `CLINIC.build` (прежний код —
  комментарием; возвращает `BuiltTables`: `clinic.patients`, `clinic['appointments']`,
  `clinic.datasets` — список, `clinic.tables` — словарь).
* Пилотный экран: колонки, формы (`build_form`), заголовки и цепочка — из описаний; у
  пациентов — отметка и «Приёмов», у приёмов — «Фото» (считает программа, видит черновики).

## 4. Углы

* Включение сортировки щелчком (`QTableView.setSortingEnabled(True)`) сразу сортирует по
  столбцу 0 — подменяло сортировку из описания (и у пациентов, где столбец 0 — отметка,
  давало ошибку). Перед включением указатель сортировки снимается (`setSortIndicator(-1)`).
* Тестовая модель «назначения» импортируется в тестах ОТНОСИТЕЛЬНО (`from ..test_services…`):
  pytest называет модуль по пакетам выше `tests` (`project_med.tests…`), абсолютный путь дал
  бы второй модуль — «Table 'test_prescriptions' is already defined».
* Итоги, которые считает база, задаются пока в `field_configs` (`sql_compute`) — их читает
  сервис при создании; с 2026-10-19 `field_configs` строятся из описания (`app/schema`).
