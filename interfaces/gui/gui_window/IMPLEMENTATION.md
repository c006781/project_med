# Окно программы (`interfaces/gui/gui_window`) — заметки о реализации

> Для разработчиков: что делает модуль, как устроен и почему. Заведён 2026-11-07 с экраном настроек;
> главное окно — разделы 3–5.
> Находки экрана настроек — `ST<n>`, главного окна — `MW<n>`.

## 1. Экран настроек (`pages/settings_page.py`)

| Что | Где |
|---|---|
| Страница, две вкладки | `SettingsPage` |
| Какое поле какой настройке соответствует | `_bind_settings_fields` |
| Чтение и запись значений | `_load_settings`, `_sawe_new_config` (имя с опечаткой, им пользуются тесты) |
| Сохранить и применить | `_save_settings` → `create_config_applier().apply_changes` → `on_settings_changed` окна |
| Проверка Диска | `TokenCheckThread`, `PathCheckThread`, `remote_folder_of` |
| Уборка | `_on_clean_photos_clicked`, `_on_clean_rows_clicked`, `confirm_cleanup` |

### 1.1 Типы значений

Значения читаются и пишутся по таблице `_bind_settings_fields`; тип задаёт вид поля: текст — `str`
без пробелов по краям, спин — `int`, флажок — `bool`, уровень — строка из списка, выбор —
`currentData`. Новое поле — создать виджет и добавить строку в таблицу.

Менеджер настроек намеренно оставляет непереводимую строку как есть (`app/config/IMPLEMENTATION.md`
§4.z), поэтому она доходит до экрана. Экран не падает: в поле показывается умолчание, в журнал —
предупреждение, а в файл значение попадёт, только если пользователь нажмёт «Сохранить». Флажки читают
строки через `to_bool` (`'on'` — истина, `'off'` — ложь, остальное — ложь).

Пустая папка копий базы при сохранении заменяется умолчанием, и поле это показывает.

### 1.2 Проверка Диска

Потоки всегда отправляют `result`: без этого исключение в `run` оставляло кнопку выключенной. Функции
`check_token`, `check_and_create_path` сами ошибок почти не бросают, но клиент создаётся и закрывается
вне их перехвата.

В поле «Удалённый путь БД» может быть и папка, и файл базы; по умолчанию там файл. Кнопка проверяет
папку (`remote_folder_of`, то же правило расширений, что у `remote_db_file_path`). Отсутствующая папка
создаётся без вопроса: так было и раньше, хотя старое описание обещало «предлагает создать».

При выходе из программы страница ждёт идущие проверки (`wait_check_threads`, по 3 с на поток; подключено
к `aboutToQuit`): поток, уничтоженный на ходу, роняет процесс. Поток не прерывается: прерванный посреди
запроса он может оставить интерпретатор в плохом состоянии. Не успел — то же сообщение Qt, что и раньше.

### 1.3 Уборка

Два действия на готовых методах, оба по схеме «список → подтверждение → удаление подтверждённого»:

| Кнопка | Метод сверки | Удаление | Что удаляет |
|---|---|---|---|
| «Очистить фото без ссылок» | `PhotoService.check_storage` | `clean_storage` | файлы папки фото без строки файла; пустые папки `app_*` |
| «Очистить записи без ссылок» | `TableEvents.find_unused` | `delete_unused` | строки таблиц «только используемые»: заметки, строки файлов (файл — после коммита) |

Список показывается целиком в прокручиваемом поле (`confirm_cleanup`), по умолчанию выбрана отмена.

Уборка не запускается (`_cleanup_blocked_reason`), если:
* файла базы нет — открылась бы новая пустая база, и все фото оказались бы «без ссылок»;
* путь к базе или папка фото в форме не сохранены — пользователь видел бы одни пути, а сверка шла бы по другим;
* есть несохранённые черновики — их ссылки ещё не в базе.

Ограничение: если сохранён путь к другой, существующей базе, а папка фото прежняя, все её файлы будут в
списке как «без ссылок». Защита — подтверждение: в окне указаны база и папка и число файлов.

### 1.4 Настройки, которые применяет не применитель

`DRAFT_MOVED_RULE`: блок `drafts` в `SETTINGS_BLOCKS`, применитель ничего не делает. Смену видит главное
окно в `on_settings_changed` (`'drafts' in changed_blocks`). `WORD_DOCUMENTS_PATH` в блоки не входит:
значение читается в момент импорта.

### 1.5 Не менялось намеренно

`_on_tab_changed` не подключён и не работает (`content_layout`, `about_title` остались от прежней
раскладки): оставлен как есть, с пометкой в докстринге.

## 3. Главное окно (`main_window.py`)

| Что | Где |
|---|---|
| Страницы и менеджер страниц | `PagesCreationMixin` |
| Сигналы страниц и шапки | `ConnectionsMixin` |
| Удаление с подтверждением | `DeleteHandlersMixin` |
| «Назад», крошки, вход на страницу | `NavigationMixin` |
| Обмен базой с Диском, копии, замена файла | `SyncMixin`; общее с командной строкой — `app/services/sync_service.py` |

### 3.1 Миксины

У миксинов нет общих имён: иначе молча работает только первый по наследованию. Так было с
`_on_download_finished` и `_on_download_error` у `SyncMixin` и `UpdateMixin` (MW2). Проверяет
`tests/test_main_window/test_main_window_mixins.py`. Новый миксин надо добавить в список этого теста.

### 3.2 Проверка обновлений при запуске

Через 1,5 с после старта (`_delayed_check_updates`). Выключают настройка `UPDATE_CHECK_ON_START` (флажок
на экране настроек) и переменная окружения `PROJECT_MED_NO_UPDATE_CHECK=1`, которая главнее настройки: так
проверочный запуск не зависит от файла настроек. Запрос идёт только в потоке `UpdateChecker`; отдельной
проверки доступности GitHub нет, она останавливала окно до 3 с. Проверка тихая: «обновлений нет» и ошибка
не показываются, только найденное обновление.

Настоящее окно для проверок запускать с этой переменной, в подпроцессе, с временными настройками, базой и
журналами (`tests/test_main_window/window_scenario.py`).

### 3.3 Установка обновления и несохранённое

`UpdateApplier` сам завершает программу через `sys.exit`, мимо `closeEvent`, на Windows и Linux. Поэтому
`_install_update`:

1. до начала задаёт те же вопросы, что при закрытии (`_resolve_unsaved_before_exit`);
2. открывает модальное окно ожидания без кнопок и без реакции на Esc (`UpdateProgressDialog`): правка, сделанная
   после вопроса, пропала бы молча. Отменить скачивание модуль обновлений не умеет;
3. при ошибке закрывает окно, работа продолжается. Черновики при «не сохранять» до выхода не очищаются:
   обновление может и не состояться.

Сигнал `download_error` — не только обрыв: отказ до скачивания, нет прав, не совпала контрольная сумма. Поэтому
заголовок «Обновление не установлено» (MW3).

Причина отката Linux показывается при старте один раз (`_show_linux_update_failure`). Подсказка о копии базы
добавляется, если причина её не содержит: откат возвращает только код (`app/UPDATER.md` §1.3, U29).

Замена файла окном (`_apply_update_file`) — путь `AppUpdater.download_update`, который сейчас никто не вызывает.
Ветка Linux в нём не могла сработать: Linux-версия запускается из исходников, выход раньше, поэтому оставлена
комментарием (MW4). Ветка Windows оставлена как есть.

### 3.4 Обмен базой с Диском (ТД-1, оконная часть)

```
_start_download
  _prepare_transfer: идёт другая работа? токен? → backup_db_before_transfer (ошибка — передача не начата)
  _set_transfer_running(True): экраны и список действий выключены
  CheckedDownloadThread (рабочая база не меняется)
    обрыв, проверка не прошла → _log_transfer_failure, _on_db_download_error: «База не скачана»
    успех → _on_db_downloaded
      совпало → без замены
      локальная новее → вопрос, по умолчанию отказ
      _confirm_db_replace: незавершённая правка, черновики, старые экраны
      install_checked_download → экраны заново → сообщение с путём копии
```

`install_checked_download`: закрыть подключения → запомнить прежний файл → `os.replace` → убрать `-journal`, `-wal`,
`-shm` → открыть и перезагрузить сервисы (`ConfigApplier.apply_database`, те же объекты, что у страниц) → убрать
запомненный. Запомненный файл нужен для отката, а не для пользователя (для него копия в `BACKUP_PATH`).

| Решение | Почему |
|---|---|
| Копия — до начала передачи, вызов в потоке окна | В-20; ошибка копии останавливает передачу до сети |
| Функции замены и копий — в `sync_service.py`, а не в окне | Те же шаги у командной строки (`download_sync`) |
| На время передачи экраны выключены, «Назад» не работает | Правка записала бы в передаваемый файл; выгрузка взяла бы несогласованный, скачивание затёрло бы правку |
| Выход и новая передача во время передачи запрещены | Поток не прервать, а уничтоженный на ходу он роняет процесс |
| Перед заменой не предлагается «сохранить» черновики | Записались бы в базу, которая сейчас будет заменена. Отказ оставляет всё как было: сохранить и скачать снова |
| Черновики и история отмены очищаются после удачной замены | Ссылаются на записи прежней базы; при сбое замены база прежняя, и они нужны |
| Скачанная база не открылась — возврат прежней | Например, база новее программы: иначе программа осталась бы без рабочей базы |
| Неполная копия прежней версии (нет места) не возвращается | Откат только если `os.replace` уже прошёл |
| `BACKUP_COUNT` негодный — старые копии не удаляются, в журнал предупреждение | Умолчание удалило бы копии по числу, которого пользователь не задавал |
| Удаляются только файлы вида `<имя> - <метка>[ (N)]<расширение>` | Остальное в папке чужое. Порядок — по метке в имени, дату файла меняет копирование |
| `download_sync` без `overwrite_newer` не затирает локальную базу, которая новее | Спросить некого; сообщает исключением |
| `.part` этой базы удаляются при старте без проверки возраста | Своё скачивание в этот момент не идёт; два окна на одну базу не поддерживаются |

Ограничения. На Windows замена проверена только подменой (`os.replace` с ошибкой): настоящую проверку проводить на
Windows (ТД-1). `close_db` закрывает сессию потока окна и пул; другие потоки не работают с базой, пока идёт передача, —
это обеспечивает окно. `prepare_download` сервиса по-прежнему отдаёт старый `DownloadThread`, окно его не использует.
Несохранённые черновики при выгрузке на Диск не попадают и вопроса об этом нет.

### 3.5 Импорт из Word

Итоги показываются в окне прогресса, рядом со статусами файлов, страницы обновляются при его закрытии (кнопка, Esc
или крестик). Окно скрыто пользователем — итоги отдельным сообщением, страницы сразу. Отменить импорт нельзя,
поэтому кнопка называется «Скрыть» (MW6). Папка выбора — `WORD_DOCUMENTS_PATH`.

### 3.6 Запасные старые экраны

Старые экраны хранят правки сами (`_has_unsaved_changes`). Перед выходом, установкой обновления и заменой базы окно
спрашивает, потерять ли их; сбой проверки считается наличием правок (MW14).
